# Фоновая догрузка истории Matrix

`matrix-history-mirror.py` помогает новому Matrix-аккаунту догрузить историю **тех же самых комнат**, в которые его пригласили со старого сервера. Скрипт обращается только к Matrix Client API; оригинальные события между серверами передаёт федерация. После начального обхода скрипт отслеживает новые события через `/sync` и периодически сверяет полную историю по `event_id`.

Используйте его при переходе на другой аккаунт или `server_name`. Для переезда
с прежними Matrix ID нужна [миграция установки](migration.md). Зеркалирование
не переносит права старого аккаунта, его контакты, устройства и сессии и не
создаёт резервную копию серверов. Сохраните исходный сервер и клиентские ключи
до проверки результата.

Интервал повторной полной сверки отсчитывается после завершения обхода всех
общих комнат. Длительная догрузка сохраняет курсоры и накопленные события,
даже если длится дольше интервала. Если аккаунт вышел из комнаты, её статус
становится `WAIT_JOIN`; сохранённый обход продолжается после возвращения.

Опциональный режим `--media-manifest` запрашивает старые локальные файлы **через новый Synapse** и проверяет, что их можно прочитать из его удалённого кэша с `allow_remote=false`. Для полного отключения старого homeserver этот режим обязателен, но требует отдельной настройки S3-провайдера и полной инвентаризации исходных медиа.

## Условия

1. Старый и новый homeserver должны федератироваться друг с другом, пока идёт догрузка.
2. Владелец самостоятельно создаёт новый аккаунт и приглашает его **в исходные комнаты**. Скрипт не создаёт копии комнат и не приглашает других пользователей.
3. Для чтения зашифрованной истории импортируйте E2EE-ключи комнат из старого
   клиента в новый, если клиенты поддерживают этот путь. Скрипт ключи не
   экспортирует и не импортирует, расшифровку не проверяет и не получает
   незашифрованные ключи комнат. Сам обход `event_id` возможен без расшифровки.
4. Для обоих аккаунтов нужны действующие Client API access token. Токены кладутся в отдельные файлы с правами `0600` либо выдаются исполняемыми credential helpers. Helper должен печатать в stdout **только access token**; он может сам обновлять OAuth token. Пароли аккаунтов скрипту не требуются.
5. Серверы должны предоставлять HTTPS с проверяемыми сертификатами. HTTP и перенаправления отклоняются; `--insecure` нет.

## Запуск

Запускайте на Linux-машине с Python 3.11–3.14 из корня репозитория. Она должна
оставаться включённой и иметь доступ к обоим API; фоновый процесс сам по себе
не настраивает автозапуск после перезагрузки. В обычном терминале запустите:

```sh
python3 deployment/matrix-history-mirror.py start
```

При первом запуске скрипт попросит HTTPS-адрес Matrix API и Matrix ID каждой
стороны, затем access token скрытым вводом. Файлы токенов создаются автоматически
с правами `0600` внутри закрытого каталога состояния; значения не попадают в
аргументы команд или журнал. Если запуск worker не завершился после сохранения
профиля, реквизиты остаются для `resume`. Ошибка до сохранения профиля удаляет
только новые файлы токенов этого запуска.

Повторный `start` в терминале использует сохранённые поля и реквизиты; явно
переданные параметры имеют приоритет. При смене URL реквизиты прежнего адреса
автоматически не используются. Для других аккаунтов нужен отдельный каталог.
Самостоятельное создание аккаунтов, приглашения в комнаты и импорт E2EE-ключей
в клиенте остаются обязательными условиями выше.

Для автоматизации без терминала все URL, Matrix ID и источники токенов передаются
явно, как раньше. Если файлы уже подготовлены, полный пример запуска:

```sh
python3 deployment/matrix-history-mirror.py start \
  --source-url https://matrix.old.example \
  --source-user @alice:old.example \
  --source-token-file ~/.config/matrix-history-mirror/source.token \
  --target-url https://matrix.new.example \
  --target-user @alice:new.example \
  --target-token-file ~/.config/matrix-history-mirror/target.token
```

Вместо `--source-token-file` или `--target-token-file` можно указать `--source-token-command /absolute/path/to/helper` или соответствующий параметр назначения. Это полезно при коротком сроке жизни OAuth-токенов. Путь к helper не должен содержать секретов. Скрипт перечитывает token files перед каждым запросом и повторно вызывает helper после HTTP 401.

```sh
python3 deployment/matrix-history-mirror.py status
python3 deployment/matrix-history-mirror.py stop
python3 deployment/matrix-history-mirror.py resume
```

Каталог состояния по умолчанию — `~/.local/state/matrix-history-mirror`;
`status`, `stop` и `resume` используют его без повторного ввода пути. Для отдельной
пары аккаунтов или прежнего нестандартного каталога передайте `--state-dir /private/path`
в каждой команде. Уже сохранённый профиль другой пары аккаунтов не перезаписывается.

`start` и `resume` запускают фоновый процесс. Его журнал находится в приватном `worker.log`; токены в журнал не записываются. SQLite-состояние сохраняется в каталоге с правами `0700`. При недоступности старого сервера состояние переходит в `WAIT_SOURCE`, а процесс повторяет подключение. После возвращения сервера сканирование продолжится с сохранённых курсоров. `stop` запрашивает остановку; уже начатый HTTP-запрос может завершаться до 25 секунд. После ручной остановки `resume` использует прежние параметры и контрольные точки.

В выводе `status` поля `state` и `running` описывают процесс. При `WAIT_SOURCE` или
`WAIT_TARGET` проверьте доступность соответствующего API; процесс повторяет
попытки. При `AUTH_REQUIRED` проверьте, что токен относится к указанному Matrix ID,
обновите приватный файл или credential helper. Не меняйте аккаунты внутри
сохранённой пары и не удаляйте SQLite-состояние ради повторной авторизации.

Отдельно для каждой комнаты выводится:

- `BACKFILLING` — история ещё просматривается;
- `LIVE` — сканирование завершено и все события, видимые исходному аккаунту, найдены у нового;
- `GAPS` — после завершённого обхода остались отсутствующие `event_id`;
- `WAIT_JOIN` — новый аккаунт ещё не вступил в эту комнату.

Число `missing_events` во время `BACKFILLING` предварительное. `GAPS` может означать задержку федерации или запрет на старую историю: при `history_visibility=invited`/`joined` новый участник обычно не увидит события до вступления. Скрипт не обходит это ограничение. Транспорт зашифрован TLS; содержимое E2EE-сообщений остаётся зашифрованным Matrix-клиентом.

Поле `media.state` отдельно показывает `NOT_CONFIGURED`, `INCOMPLETE` или `VERIFIED_LOCAL_ORIGIN`. Совпадение event ID при `LIVE` не проверяет вложения.

После перезагрузки или аварийного завершения проверьте `status`. Если процесс
не работает, выполните `resume` с прежним каталогом состояния. Если `running=true`,
второй процесс не нужен. `LIVE` относится к завершённой сверке видимых событий;
при продолжающейся переписке скрипт должен оставаться запущенным до окончательной
проверки. Старые архивы и данные источника он не удаляет.

## Перед отключением старого сервера

Для нужных комнат дождитесь `LIVE`, откройте несколько старых сообщений новым аккаунтом и проверьте расшифровку после импорта ключей. Оригинальные события, уже полученные новым homeserver, остаются в его БД после отключения старого. Старые MXID и room ID при этом **не переименовываются**; учётные записи старого сервера не начинают обслуживаться новым.

Отдельно проверьте вложения. Ссылки `mxc://old.example/...` требуют доступного старого media origin, пока новый Synapse их не закэширует. Даже статус `VERIFIED_LOCAL_ORIGIN` относится только к ID из переданного manifest и не доказывает, что все медиа старого сервера перечислены или что копия уже находится в S3. Зашифрованные ссылки на вложения находятся внутри E2EE-содержимого, поэтому серверный обход событий не может надёжно перечислить их; для полноты нужен серверный список **всех локальных медиа**, включая загрузки из зашифрованных комнат. Для комнат с `GAPS` старую историю также нельзя считать перенесённой. Если участники находятся только на старом homeserver, после его выключения они не смогут продолжать чат, пока не перейдут на доступный сервер.

## Общий S3-бакет

Два независимых Synapse могут хранить медиа в одном S3-бакете, если каждому задан **собственный неизменяемый `prefix`** (`old/`, `new/`) и отдельные права доступа к своему префиксу. Один префикс на два независимых homeserver не используется. При переносе *того же* homeserver на другую машину его база данных и префикс переезжают вместе, а запись на старой машине останавливается до запуска нового писателя.

Общий бакет не объединяет медиатеки. Локальное медиа Synapse учитывает в `local_media_repository`, а скачанное с другого сервера — в `remote_media_cache` с соответствием MXC и локального файлового ID. Поэтому новый сервер не начнёт обслуживать `mxc://old.example/...` только оттого, что видит старый префикс S3. При полном выключении старого *логического* homeserver байты нужно хотя бы один раз перенести в кэш нового сервера; совместное использование бакета не устраняет этого шага.

На новом Synapse S3-провайдер должен иметь `store_remote: true`, `store_synchronous: true`, собственный `prefix`, приватный бакет и HTTPS endpoint с проверкой сертификата. `media_retention.remote_media_lifetime` оставьте unset/null, не вызывайте очистку remote media cache. БД нового Synapse и объекты S3 нужно сохранять вместе: без таблицы `remote_media_cache` файлы старого origin не связываются с их MXC URI.

Для Synapse-источника подготовьте приватный TSV с `media_id`, размером в байтах и необязательным SHA-256. Порядок столбцов фиксирован; разделитель — табуляция. Например, выгрузите IDs и размеры из *старой* БД Synapse через `psql` на старом сервере (реквизиты БД передаются через стандартный `PGPASSFILE`, а не в командной строке):

```sh
umask 077
psql -A -t -F $'\t' -c 'SELECT media_id, media_length FROM local_media_repository WHERE url_cache IS NULL ORDER BY media_id' > source-media.tsv
chmod 600 source-media.tsv
```

Сверьте число строк с `SELECT count(*) ... WHERE url_cache IS NULL` и полноту старого media store. Передайте manifest на машину скрипта по SSH. Затем добавьте к команде `start`:

```sh
  --media-origin old.example \
  --media-manifest /private/path/source-media.tsv
```

При `resume` скрипт повторяет неудачные файлы. Для каждого ID он сравнивает размер и SHA-256 полученных через новый Synapse байтов, затем повторяет запрос с `allow_remote=false`. При указанном в третьем столбце исходном SHA-256 он сверяет и его. Ошибки остаются в `media.errors`; статус `VERIFIED_LOCAL_ORIGIN` появляется только когда все строки manifest проверены.

Перед выключением источника обязательно проведите пробу при заблокированном доступе нового Synapse к старому origin: откройте старые вложения в клиенте, сверяйте случайную выборку `allow_remote=false`, проверьте объекты в новом S3-префиксе и резервную копию БД. Вложения с MXC других отключаемых серверов в manifest старого origin не входят.
