# Подключение и восстановление хранилищ

Команды выполняются в SSH-сессии на VPS. Приватные env-файлы не исполняются
через `source`; значения не передаются аргументами команд. Используйте права
0600 и каталог 0700. Проверяйте выбранную конфигурацию на своём сервере; изолированный тест не заменяет приёмку.

## S3 при первоначальной установке

Выберите s3 при init либо задайте MEDIA_MODE=s3 до первого up. Заполните в
settings.env S3_BUCKET, S3_REGION, S3_ENDPOINT_URL, S3_ACCESS_KEY_ID,
S3_SECRET_ACCESS_KEY и отдельный S3_PREFIX, заканчивающийся `/`.
Endpoint — HTTPS origin, без пароля и пути. Region используется при подписании
запросов и не выводится автоматически из имени endpoint.

Перед стартом установщик проверяет подписанный доступ к bucket. При отказе
объясняет дальнейший путь и сохраняет ключи, настройки и данные. До первой
успешной установки можно продолжить локально:

```bash
sudo bash /opt/matrix-stack/install.sh media-local
sudo bash /opt/matrix-stack/install.sh up
```

Ожидается media_local_selected, затем обычный успешный up. S3-параметры остаются
в приватном settings.env для дальнейшего подключения. Эта операция не выключает
S3 действующей установки: сначала нужно подтвердить наличие всех локальных
оригиналов. HEAD не доказывает права PUT/GET или успешную выдачу вложений Matrix;
эти сценарии проверяются отдельно.

## S3 после локальной установки

Создайте на VPS `/root/matrix-s3.env` с правами 0600 и только шестью S3-полями
из предыдущего раздела. Не включайте DOMAIN, OAuth или пароли БД.
Для каждого сервера используйте отдельный prefix. Изменять bucket/endpoint/
region/prefix работающего S3 обычным редактированием settings.env запрещено:
смена назначения требует отдельного переноса данных.

```bash
sudo bash /opt/matrix-stack/install.sh media-s3 /root/matrix-s3.env
sudo bash /opt/matrix-stack/install.sh check
```

Сначала проверяется S3 без изменения локальной установки. Затем создаётся
согласованный backup и проверяется восстановление обеих БД. Synapse
останавливается на время копирования файлов. Все локальные файлы сохраняются.
Для каждого объекта проверяется SHA256 после GET; чужой объект с другим
содержимым не перезаписывается. Ожидается media_s3_connected с
files_verified и local_files_retained=true. После старта дополнительно проверьте
скачивание прежнего вложения и загрузку нового из Matrix-клиента.

`stages/media-transfers/checkpoint-<идентификатор>.json` сохраняет прогресс до PUT и после
проверки GET. Потерянный ответ PUT не создаёт второй объект при повторе.
При обработанном отказе возвращаются прежние локальные настройки; исправьте
приватный S3-файл и повторите ту же команду. При SIGTERM, отключении SSH или
перезагрузке может остаться media_transition_pending:

```bash
sudo bash /opt/matrix-stack/install.sh media-recover
sudo bash /opt/matrix-stack/install.sh media-s3 /root/matrix-s3.env
```

Первая команда возвращает сохранённые локальные настройки и запускает стек
без обращения к S3. Вторую выполняйте после восстановления доступности S3.
Если переключение уже зафиксировано и pending отсутствует, продолжение —
`sudo bash /opt/matrix-stack/install.sh up`. При конфликте разных удалённых
данных сохраните checkpoint и выберите новый пустой prefix; новый перенос
получит отдельный checkpoint. Уже подключённое назначение S3 этой командой не меняется.

Если SSH оборвался, сначала выполните `sudo bash /opt/matrix-stack/install.sh status`
и `sudo bash /opt/matrix-stack/install.sh check`: операция могла завершиться на
сервере. При успешном `check` и сохранённом MEDIA_MODE=s3 повторное подключение
не требуется. HTTP401 при скачивании медиа означает проблему авторизации:
обновите сессию клиента или войдите снова, затем повторите запрос. Не удаляйте
локальные файлы и не меняйте S3 credentials ради обхода этой ошибки.

Synapse хранит новые медиа локально и в S3 синхронно. Не удаляйте локальные
оригиналы ради освобождения места: пока полный backup удалённых объектов и
восстановление приложения не проверены, это нарушит условия восстановления.
Локальный archive сам по себе не доказывает полноту копии S3. Перенос не является
зеркалом или системой исторических резервных копий.

Проверьте старые и новые вложения, полноту внешней копии и восстановление. Успешный S3 probe не подтверждает эти проверки.

## Внешняя PostgreSQL

Начальная установка требует отдельного пустого кластера с административным
доступом. POSTGRES_SSL_MODE=verify-full проверяет CA и hostname; пустой
POSTGRES_SSL_ROOT_CERT использует системный CA bundle. Для частного CA задайте
абсолютный путь к его PEM на VPS. CA копируется в конфигурацию и подключается
к Synapse, MAS и postgres-client. Не отключайте проверку TLS для обхода ошибки.

Установка сохраняет checkpoint `config/external-postgres-owner.json`,
создаёт роли и метки владения одной транзакцией, затем БД с владельцами
synapse/mas и UTF8/C. После потери ответа повторный `up` в том же каталоге
продолжает создание своих объектов, не меняет прежние пароли и не присваивает
чужие роли/базы. Сохраните checkpoint; не удаляйте роли или базы ради повтора.
При ошибке проверьте приватные реквизиты, hostname, CA и сетевой доступ, затем
Повторите `sudo bash /opt/matrix-stack/install.sh up`. Ошибка совместимости
или чужие объекты требуют отдельного пустого кластера, а не автоматической очистки.
Для действующей локальной установки простая смена POSTGRES_MODE запрещена.
Внешние копии и их ограничения описаны в [backup.md](backup.md).
generate/up отказываются менять host/port уже подключённой внешней БД.
Проверяется сохранённый ownership checkpoint, для старого комплекта — прежняя
connection identity из homeserver.yaml. Реквизиты не сравниваются и не выводятся.
При ошибочном редактировании восстановите POSTGRES_HOST/POSTGRES_PORT из
проверенной private копии и повторите `sudo bash /opt/matrix-stack/install.sh up`.
Перенос external→external пока не реализован; новое имя хоста само по себе
не переносит прежние данные. Изменение IP backend за прежним hostname управляет
оператор кластера; оно не подтверждает сохранность данных автоматически.

Перед SQL с паролем требуются права установки session logging controls.
При отказе psql/ON_ERROR_STOP прекращает работу до отправки password statement;
сервер не меняет глобальную logging policy. Те же controls используются в
локальном init-db.sql. Они предотвращают запись password statements при DDL
ошибках; аудит провайдера и pgAudit требуют отдельной оценки администратора.
Администратор dedicated cluster может выдать ограниченные права отдельной
installer_admin (замените имя своей роли):

```sql
GRANT SET ON PARAMETER log_statement, log_duration,
  log_min_duration_statement, log_min_duration_sample,
  log_statement_stats, log_parser_stats, log_planner_stats, log_executor_stats,
  log_error_verbosity, log_min_error_statement TO installer_admin;
```

Сама роль также должна иметь необходимые CREATE ROLE/CREATE DATABASE права.
Если установлен pgAudit, нужен SET для его pgaudit.log; обычный PostgreSQL
без расширения этого параметра не требует. Обязательный внешний audit/proxy,
не позволяющий скрыть secret SQL statements, требует отдельного решения с
оператором сервиса; не обходите отказ установщика. Правила controls —
[PostgreSQL logging](https://www.postgresql.org/docs/18/runtime-config-logging.html)
и [GRANT SET](https://www.postgresql.org/docs/18/sql-grant.html).

### Перенос существующих локальных баз

Поддержан local PostgreSQL18 → отдельный external PostgreSQL18 с verify-full,
для local/S3 media. Используется static Vault/cache интеграция; внешний Vault требует отдельной копии и проверки доступа. Смена одного внешнего кластера на другой
пока не реализована. Обратный путь external→local — явное восстановление
полного снимка в пустую staged установку через `restore-local`; подробности,
команды и ограничения в [backup.md](backup.md#внешняя-postgresql-восстановление-в-локальную).
Перед началом все Matrix writers должны работать и пройти up/check;
перенос намеренно частично остановленной установки пока запрещён.
Медиа остаётся на прежнем месте, Matrix server_name и внутренние ключи сохраняются.

Создайте по SSH `/root/matrix-postgres.env` (root-owned600, каталог700):

```dotenv
POSTGRES_HOST=db.example.org
POSTGRES_PORT=5432
POSTGRES_SSL_MODE=verify-full
POSTGRES_SSL_ROOT_CERT=/root/dedicated-db-ca.pem
POSTGRES_ADMIN_USER=postgres
POSTGRES_ADMIN_PASSWORD=EXAMPLE_REPLACE_PRIVATELY
```

CA path должен существовать на этом VPS; для публичного CA оставьте поле пустым.
Клиент позднего переноса и probe application roles также подключает
системный CA bundle VPS при пустом поле. Передача через readonly bind mount и
`verify-full` сохраняет проверку сертификата и hostname; отсутствие source CA
не создаёт автоматически пустой каталог. Проверьте TLS и настоящее SQL-подключение
для выбранного CA: тест аргументов не заменяет внешнюю проверку.
Передайте файл по SSH/SCP, редактируйте приватным редактором; не вводите пароль
в командную строку или историю shell. Выполняйте после обновления установщика:

```bash
sudo bash /opt/matrix-stack/install.sh database-external /root/matrix-postgres.env
sudo bash /opt/matrix-stack/install.sh check
```

Ожидается database_external_connected/databases2/local_data_retained=true.
Проверяются TLS/major18/владение ролями и пустота назначения; также
вход обоих application roles с сохранёнными паролями до остановки source.
Для администратора кластера используйте отдельную роль, synapse/mas зарезервированы.
Чужие роли/данные
не удаляются. Создаётся и проверяется предварительная копия; затем writers
останавливаются до финального согласованного снимка, импорта обеих БД,
сравнения inventory и запуска. Перерыв зависит от объёма/скорости; нулевой
простой этой операции не поддержан. Холодные data/postgres и копии сохраняются.
final_freeze_window_seconds — время от начала финальной остановки
до проверки запущенных writers, включая ожидание/recovery. Предварительные
backup/restore-check имеют свои остановки, не включённые в это поле. Clock
adjustments влияют на wall-clock измерение; старый journal без даты возвращает null.
Проверьте старые аккаунты, зашифрованную комнату, прежнее и новое вложение клиентом.
Успешное число строк само по себе не доказывает восстановление пользовательских ключей.

Ошибки реквизитов/TLS до подготовки не меняют локальные настройки. Исправьте
файл и повторите database-external. Для своего частично созданного назначения
сохраните stages/database-targets с checkpoint владения. При ошибке после
остановки или разрыве SSH не запускайте другой writer:

```bash
sudo bash /opt/matrix-stack/install.sh status
sudo bash /opt/matrix-stack/install.sh database-recover
```

Если во время `database-recover` проверка S3 отказывает перед запуском,
обе импортированные БД и private checkpoint сохраняются. Восстановите доступ
к S3 и повторите **database-recover**, затем `check`. Обычный `up` при pending
переносе БД отказан. Сообщение S3 указывает точную команду
продолжения для этого состояния. После начала activation команда не повторяет
SQL-импорт и не возвращает устаревшую локальную БД; не удаляйте checkpoint
и не выбирайте media-local ради обхода отказа работающего S3-хранилища.

Работающий прежний клиент PostgreSQL блокирует recovery до его завершения;
журнал не удаляйте. До активации назначения можно отменить перенос командой
`sudo bash /opt/matrix-stack/install.sh database-abort`: вернутся исходные
локальные настройки и прежде запущенные writers; внешние данные сохранятся.
После начала запуска новых writers abort запрещён: там уже могли появиться
записи. Продолжайте database-recover, не возвращайтесь к устаревшему локальному
снимку. Обратный перенос после новых записей требует новой согласованной копии
назначения и отдельной проверенной процедуры; автоматической команды пока нет.
После отмены назначение с копией не считается пустым — используйте новый
пустой dedicated cluster для новой операции. Повтор recover после успеха
сообщает pending=false; identity не меняет и данные не импортирует повторно.

При подключённом static Vault перед публикацией новых настроек кэш помечается
dirty. После успешного up обычный CAS/readback сохраняет новый snapshot с
прежним owner/path/AppRole. Отказ Vault не удаляет локальные runtime файлы:
сервер может продолжить, но старый snapshot не считается пригодным для recovery.
Восстановите доступ и выполните `sudo bash /opt/matrix-stack/install.sh vault-sync`.
Preactivation abort возвращает исходные config/права и прежнюю cache запись;
он не удаляет удалённые версии Vault и данные назначенной БД.
