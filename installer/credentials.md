# Управление ключами доступа и паролями

Руководство для администратора управляемой установки: сменить ключи S3-медиа, пароли приложений
PostgreSQL или пароль первоначального `matrix-admin`. Операции выполняются по SSH с правами root и
могут прерывать работу служб. Перед началом выполните `sudo misbot status`, завершите незаконченные
операции и обеспечьте запас места для согласованной резервной копии.

| Что меняется | Команда | Что делает восстановление после прерывания |
| --- | --- | --- |
| Пара ключей S3-медиа при прежнем bucket/prefix | `credentials s3 rotate --config PATH` | `credentials s3 recover` применяет сохранённую новую пару |
| Пароли ролей PostgreSQL `synapse` и `mas` | `credentials database rotate` | `credentials database recover` завершает ту же смену с сохранёнными новыми паролями |
| Пароль первоначального `matrix-admin` | `credentials admin set --input PATH` | `credentials admin recover` возвращает сохранённый прежний пароль |

Команды в таблице запускаются как `sudo misbot …`. Их восстановление устроено по-разному: не
подменяйте файлы секретов вручную и используйте раздел своей операции. Для пароля обычного
пользователя см. [пользователи](users.md#сменить-пароль-обычного-пользователя), для личного
административного доступа — [панель](admin-panel.md#личный-аккаунт-администратора), для подключения
и синхронизации Vault — [хранилища](storage.md).

## Ключи доступа к S3-медиа

Операция меняет только пару S3 access key/secret key уже работающей установки. Bucket, region, HTTPS
endpoint и prefix должны совпасть с прежними. Перенос в другой bucket/prefix этой командой не
выполняется. Сначала у провайдера создайте новую пару с теми же правами чтения и записи, оставляя
прежнюю пару действующей до успешной проверки старых и новых вложений.

На VPS подготовьте root-owned файл через редактор, без значений в shell/history:

```bash
sudo install -m 600 /dev/null /root/matrix-s3-next.env
sudo nano /root/matrix-s3-next.env
```

Заполните все шесть имён из [S3 шаблона](storage.md#s3-при-первоначальной-установке).
Не меняйте destination поля. Затем:

```bash
sudo misbot check
sudo misbot credentials s3 rotate --config /root/matrix-s3-next.env
sudo misbot check
```

Установщик проверяет HEAD/list/read, создаёт резервную копию и проверяет все включённые дампы,
проверяет PUT/GET отдельного вымышленного объекта, останавливает Synapse и применяет новую пару.
Используется прежний конкретный image ID: компоненты и Matrix identity не обновляются. Данные,
локальные медиа, ключи шифрования и другие ключи доступа сохраняются. Успех —
`s3_credentials_changed`, `passed=true`, `changed=true`; затем проверьте загрузку нового фото и
чтение старого. Та же пара выдаёт `changed=false` после проверки доступа, без перезапуска.

При ошибке до применения исправьте закрытый файл ввода и повторите исходную команду. При pending
журнале обычные up/backup/update/изменения хранилищ запрещены:

```bash
sudo misbot status
sudo misbot credentials s3 recover
sudo misbot check
```

Обновление проверяет незавершённую смену S3 ключей до обращения к БД и изменения файлов: сначала
выполните указанную `s3-credentials-recover`. `credentials s3 recover` восстанавливает и остальные
контейнеры, если после прерывания выполнялся `down`, с прежним конкретным образом Synapse и
закреплёнными версиями компонентов. Вручную запускать Synapse для этого не требуется. Восстановление
использует ту же сохранённую новую пару, без ручного возврата старых файлов и без старта Synapse с
неопределённой конфигурацией. Если новые ключи отозваны или S3 недоступен, восстановите доступ к
этой паре у провайдера, сохраните приватный checkpoint и повторите recover. Старую пару отзывайте
только после фактической проверки. Для полного возврата используйте проверенную согласованную копию
и действующие ключи доступа соответствующего ресурса.

Данные проверочного объекта находятся в приватном `stages/s3-credentials/<ID>/probe.json`. Если
DeleteObject запрещён, проверочный объект с вымышленными байтами может остаться; остальные медиа не
удаляются. После разрешения удаления выполните:

```bash
sudo misbot credentials s3 cleanup
```

Отказ этой команды показывает именно `s3-credentials-cleanup` с полным путём установки. Если смена
ключей ещё pending, сначала предлагается `s3-credentials-recover`. Ошибка до создания checkpoint
предлагает повторить исходную команду с тем же закрытым файлом ввода; секретные значения в сообщении
отсутствуют.

Удаляются только объекты из собственных каталогов учёта с точным UUID/identity; известный VersionId
удаляется отдельно. Потеря ответа PUT в бакете с версиями может оставить прежнюю неизвестную версию:
её очистка здесь не реализована, проверьте историю версий у провайдера по приватному каталогу учёта.
Успешный DeleteObject не подтверждает удаление всех версий.

Внешние копии используют отдельный S3 env: эта операция его не изменяет. Перед отзывом общего
старого ключа обновите их закрытый env-файл и проверьте создание и получение внешней копии;
расписание описано в [backup.md](backup.md). Доступ к Vault синхронизируется после проверки; при
недоступности Vault сохраняются локальные файлы и отметка для последующей синхронизации. Неизвестные
версии объектов после потери ответа PUT проверяйте отдельно у провайдера.

## Пароли приложений PostgreSQL

Операция требует локального MAS (`MAS_MODE=local`). При внешнем MAS она
отказывает до изменения паролей и баз; обслуживайте его реквизиты отдельно.

Команда генерирует случайные пароли двух фиксированных ролей `synapse` и `mas`, меняет их одной
транзакцией и сохраняет соответствующие локальные файлы. Поддержаны установленная локальная
PostgreSQL и тот же выделенный внешний кластер с сохранённым ownership checkpoint. Пароль
администратора PostgreSQL и адрес кластера этой командой не меняются.

В SSH-сессии на VPS с работающей установкой:

```bash
sudo misbot check
sudo misbot credentials database rotate
sudo misbot check
```

Все службы должны быть готовы; завершите предыдущие операции восстановления
или переноса. Установщик проверяет соединение и session privacy PostgreSQL,
создаёт резервную копию, проверяет восстановление обеих БД, затем останавливает
пишущие службы. Во время операции сообщения и новые входы временно
недоступны. Дождитесь окончания проверок; успешный результат —
`database_passwords_changed`, `passed=true`, код 0, затем `public_checks=true`.
Продолжительность зависит от размера БД и готовности контейнеров. Не запускайте вторую
операцию параллельно.

Пароли не нужно вводить или копировать в shell: они создаются автоматически и
передаются PostgreSQL через stdin. Локальные `secrets/db_synapse` и
`secrets/db_mas` обновляются атомарно по отдельности; приватный checkpoint
позволяет закончить операцию при сбое между этими записями. Identity, signing
keys, пользовательские пароли, OAuth-привязки и данные этой операцией не меняются.
Службы после проверки используют новые пароли; прежние клиентские сессии
Matrix не отзываются.

Повтор `sudo misbot credentials database rotate` после успеха означает **ещё одну новую смену**. При
незавершённой операции обычный запуск, резервная копия, обновление и смена хранилища блокируются.
Проверьте состояние и закончите ту же смену:

```bash
sudo misbot status
sudo misbot credentials database recover
sudo misbot check
```

`status` показывает `database_password_recovery_pending` и точную команду.
Восстановление применяет **те же новые пароли**, повторно создаёт конфигурации и
проверяет службы. Это работает и когда соединение потерялось после COMMIT:
ответ SQL не определяет, какие пароли реально применились. После успеха повтор
recover выдаёт `pending=false`, `changed=false` без новой смены. Не возвращайте
старые файлы паролей вручную: БД уже могла принять новые. Если соединение/TLS
или место недоступны, исправьте причину и повторите recover; сохраните БД,
исходные настройки, проверенную копию и каталог `stages/database-passwords`.
SIGTERM/SIGINT оставляют checkpoint для явного recover; SIGKILL не гарантирует
сообщение перед завершением. Разрыв SSH также не является свидетельством
успеха: после возврата сначала выполните `status`.

Для внешней БД нужны исходные отдельные административные credentials и права
`ALTER ROLE`/session privacy; не используйте роль приложения вместо
администратора. Проверка принадлежности обеих ролей/БД и изменение выполняются
в одной транзакции. Недоступный обязательный PostgreSQL не заменяется пустой
локальной базой. Зеркала и автоматический перенос на другой кластер этой
операцией не выполняются.

Vault получает обновлённый snapshot после успешной смены. Его недоступность оставляет локальные
runtime-файлы и отметку для синхронизации; повторите `sudo misbot credentials vault sync` после
восстановления связи. Не восстанавливайте устаревший snapshot поверх незавершённой смены. Копия
перед изменением содержит старые пароли и БД; для полного возврата восстанавливайте согласованный
архив в отдельную машину по [инструкции копий](backup.md), не подменяйте только пароль работающего
кластера. Файлы checkpoint содержат секреты: права 600, каталог 700, вне Git/чата.

Операция не меняет пароль администратора PostgreSQL, OAuth и ключи S3. После успеха проверьте вход,
отправку сообщения и доступ к прежним данным.

Если pending checkpoint содержит несовместимый формат паролей, выполняйте
recovery из доверенного распакованного комплекта:

```bash
sudo python3 /root/matrix-installer/pg_credentials.py --directory /opt/matrix-stack recover
sudo misbot --directory /opt/matrix-stack update apply --source /root/matrix-installer
sudo misbot check
```

Замените `/root/matrix-installer` путём своего распакованного проверенного
комплекта. Recovery сохраняет новую пару в каноническом формате 64 hex-символов
до её применения в БД; прерывание на любом из этих шагов допускает повтор.
Checkpoint сохраняет эту же пару при recover. Не обновляйте исходники
вручную внутри работающей установки и не удаляйте pending ради update.

## Пароль первоначального администратора

Команда `sudo misbot credentials admin set --input PATH` меняет только пароль `matrix-admin` в MAS и
его сохранённую копию. Matrix server_name, ключи, OAuth-привязки, пароли PostgreSQL и ключи доступа
к внешним ресурсам этой операцией не изменяются. Пароли двух приложений PostgreSQL меняет отдельная
операция выше; смена реквизитов OAuth пока не реализована отдельной командой; S3-медиа меняется
операцией выше.

## Подготовка и смена

В SSH-сессии на установленном VPS подготовьте файл через редактор:

```bash
sudo install -m 600 /dev/null /root/matrix-admin-password.json
sudo nano /root/matrix-admin-password.json
```

В файле должна быть ровно одна строковая настройка `password`, например:

```json
{"password":"Replace-this-fictional-example_123!"}
```

Введите свой новый пароль длиной 16–1024 символа без управляющих символов.
Не вставляйте реальный пароль в команду shell или чат. Файл должен принадлежать
root и иметь права 600; symlink и доступ группе/остальным запрещены.

```bash
sudo misbot credentials admin set --input /root/matrix-admin-password.json
```

Перед изменением установщик создаёт согласованную резервную копию и проверяет её восстановление.
Этот этап кратко останавливает пишущие службы; затем их предыдущее состояние возвращается. Для самой
смены пароля MAS и Synapse должны работать; команда ждёт готовности всех служб после резервной копии
и перед сообщением об успехе. readiness проверяется до завершения checkpoint: если после применения
пароля службы не готовы, выполняется возврат старого. Если службы не готовы и при восстановлении,
сохраняется незавершённая операция для следующего recover. SIGTERM/SIGINT запускают обработку
прерывания; после SIGKILL требуется явное восстановление ниже. Пароль передаётся через stdin и тело
внутреннего API-запроса, без секретов в аргументах процессов или выводе установщика.

Успех: `administrator_password_changed`, `passed=true`, код завершения 0. В отдельной новой сессии
браузера войдите на `https://admin.example.org` с новым паролем; замените example.org своим доменом.
Рабочая браузерная сессия сама по себе не подтверждает новый пароль. Выполните `sudo misbot check`.
Операция не является командой отзыва всех токенов; порядок отзыва сессий нужно проверять отдельно
для выбранной версии MAS.

Повтор с тем же сохранённым паролем откажет без новой смены. При слишком
коротком пароле или неправильном JSON исправьте приватный файл и повторите.
Если MAS отклоняет сложность пароля, выберите более длинный случайный пароль.
Неверный ввод, сообщение о его причине и повтор проверяются отдельно от успеха.

## Сбой и восстановление доступа

При обработанной ошибке установщик пытается вернуть прежний пароль. При
таймауте после применения нового пароля невозможно судить об успехе только
по соединению: сохранённый приватный checkpoint позволяет вернуть старый.
Если MAS недоступен или процесс прерван, состояние остаётся pending:

```bash
sudo misbot credentials admin recover
```

Успех: `administrator_password_recovered`, `passed=true`. Войдите заново со старым паролем из своего
менеджера паролей. Установщик сохраняет его в `secrets/admin-access.json`; содержимое файла не
включайте в диагностику. После восстановления можно повторить `sudo misbot credentials admin set
--input PATH` с исправленным файлом.

Если MAS/Synapse остановлены, сначала верните работающие службы из сохранённой
конфигурации:

```bash
sudo docker compose --project-directory /opt/matrix-stack -f /opt/matrix-stack/compose.yaml up -d synapse mas
sudo misbot credentials admin recover
```

Существующую отключённую или неадминистративную учётную запись команда не
перезаписывает. Для неё сначала восстановите административный доступ штатными
инструментами MAS. Не создавайте новую установку и не удаляйте БД/ключи.

Приватные файлы восстановления находятся в `stages/credentials/`; они содержат старый и новый
пароли. Держите каталог и резервные копии закрытыми. После проверки нового доступа удалите файл
ввода `/root/matrix-admin-password.json`. Checkpoint и копии удаляйте только после проверки доступа
и пригодности нужной копии; повторный запуск установщика не удаляет их автоматически.

## Проверка результата

После смены пароля проверьте новый вход в отдельной сессии, после смены реквизитов хранилища —
чтение прежних и запись новых данных. `misbot check` проверяет доступность служб; проверку клиента и
внешнего ресурса он не заменяет.
