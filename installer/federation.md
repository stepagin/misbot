# Федерация и межсерверный протокол Misbot 1

Руководство для администратора: разрешить связь с другим Matrix-сервером, согласовать её с другой
установкой Misbot и продолжить незавершённое подключение. Ниже сначала описаны действия оператора,
затем протокол и постоянное состояние.

Продукт: **1.2.0**. Версия протокола Misbot: **1**, независимо от Matrix и формата конфигурации. Это
протокол Misbot; схема HTTP — [OpenAPI](misbot-api.openapi.json).

Управлять федерацией можно по SSH или в личном зашифрованном чате [панели администратора](admin-panel.md): `помощь` → `федерация`. На новой установке это
`@admin-panel:<домен>`; обновлённая сохраняет прежний адрес, включая `@federation-bot`, и его ключи
шифрования.

## Выбрать способ подключения

Подключение серверов выполняется двумя способами:

* `sudo misbot federation add --server example.net` добавляет только локальную запись allowlist.
* `sudo misbot federation invite --server example.net` инициирует взаимное согласование двух экземпляров.

В терминале команды показывают ход операции и результат обычным текстом. Для технического вывода
добавьте `--json`; при перенаправлении вывода в файл или скрипт прежний JSON сохраняется
автоматически. Локальное добавление не требует Misbot API другого сервера. Согласуйте с его
администратором встречное разрешение; одной местной записи недостаточно для проверки обмена
сообщениями.

Перед изменением выполните `sudo misbot status`: закончите незавершённые операции и обеспечьте место
для согласованной копии. Применение местной политики перезапускает затронутые службы. После
согласования обеих сторон создайте или используйте реальную межсерверную комнату и проверьте
приглашение, вступление и доставку сообщения. Статус `connected` подтверждает применение политики;
правила комнаты, членство и поддержка клиента проверяются отдельно.

## Проверить удалённый сервер

Matrix server_name здесь — доменное имя без схемы/пути/порта, в соответствии с действующей моделью установщика. IP и произвольные API URL не принимаются. Другие формы Matrix server_name этим продуктовым маршрутом не поддерживаются.
Проверка `sudo misbot federation check --server example.net` показывает синтаксис, Matrix discovery и HTTPS версии endpoint, отдельно Misbot discovery/TLS и присутствие в локальной политике. `federation_exchange: not_verified` означает, что комнаты/пользователи по федерации не проверялись. DNS/timeout не означают отсутствие сервера.
Перед приглашением Misbot проверяет `/.well-known/misbot`, версию протокола, фиксированный API path, identity, поддержку срока 30 суток и объявленную возможность `federation-invites`. Обычный Matrix-сервер без Misbot не принимает такие приглашения: при отсутствующем, некорректном или несовместимом discovery заявка не создаётся и подписанный POST не выполняется. Состояние `invitation` в результате `check` содержит `supported`, `ready`, `expires_after` и безопасный `code`, если приглашение пока недоступно. Эта проверка не отправляет приглашение; при подтверждении проверки выполняются повторно.
`misbot_not_found` означает HTTP 404 по Misbot discovery; `invalid_misbot_discovery` — непригодный ответ; `invitation_unsupported` — отсутствие заявленной возможности в корректном discovery; `remote_api_disabled` — явное выключение удалённого API. Сетевые ошибки и временный HTTP 503 остаются отдельными причинами, не доказательством отсутствия Misbot.

## Локальная политика и recovery

`sudo misbot federation servers` показывает FEDERATION_SERVERS из `settings/policy.env` (либо прежнего settings.env).
`federation add/remove --server DOMAIN` сохраняет остальные записи, делает согласованную копию и проверяет восстановление, сохраняет прежние пользовательские/generated настройки в приватном `stages/federation/ID`, обновляет только политику Synapse и каталог комнат Web, перезапускает Synapse/Web и проверяет ответ Synapse.
Повтор add/remove безопасен. Удаление последней внешней записи оставляет собственный домен: федерация не открывается всем.
Matrix identity, БД, медиа, OAuth и ключи не меняются.
При прерванной публикации используйте `sudo misbot federation recover`; для возврата прежнего локального набора — `sudo misbot federation rollback`.
Сначала дождитесь окончания busy операции; не удаляйте lock.
Ручные изменения проходят `misbot config validate` и штатный `misbot config apply`, как описано в [конфигурации](configuration.md).

## Заявки и подтверждение

1. На A: `sudo misbot federation invite --server b.example.org` (местное одобрение A).
2. На B: `sudo misbot federation requests`; затем `sudo misbot federation requests approve --request MB-0123456789abcdef0123456789abcdef`.
3. На каждой стороне: `sudo misbot federation requests retry --request MB-0123456789abcdef0123456789abcdef` для продолжения и запроса удалённого статуса.
4. `sudo misbot federation peers` показывает согласованные identities. `requests status --request ID` читает локальный checkpoint.

ID имеет вид `MB-` и 32 строчных hex символа, сохраняется на обеих сторонах. Срок новой заявки —
**30 суток**, UTC Unix timestamp в протоколе и JSON-статусе; бот и терминал показывают время МСК
(UTC+3). Возможности протокола v1: только взаимный allowlist и согласованная bot identity.
Состояния: `pending`, `accepted`, `applying`, `partially_applied`, `connected`, `rejected`,
`expired`, `cancelled`. `connected` подтверждает применение политики обеими сторонами через
подписанный статус. Это **не** приёмка федеративных комнат и пользователей. Неатомарность двух
серверов отражается в local_applied/remote_applied. Потеря ответа сохраняет заявку; retry не создаёт
вторую заявку того же исходящего подключения. Для одного сервера допускается одна активная заявка.
Повторное приглашение отклоняется до создания операции; продолжение доставки выполняется через
`requests retry --request ID`. При существующей входящей заявке нужно открыть и явно одобрить её.
Новые исходящие заявки создаются не чаще одной в минуту для всей установки; ограничение хранится на
диске и действует после перезапуска и ошибки доставки. Получатель также ограничивает новые
приглашения от одного server_name одной минутой. Если две установки создали заявки до доставки друг
другу, меньший ID становится общей заявкой. Вторая сохраняется как скрытый checkpoint отмены;
принимающая сторона явно одобряет выбранную входящую заявку. Одобрение не переносится автоматически.
Уже одобренная или применяемая операция требует продолжения через retry/recovery. Отказ: `requests
reject --request ID`; отзыв исходящей: `requests cancel --request ID`. Отзыв скрывает заявку у обеих
сторон после доставки. Отклонение уведомляет отправителя и допускает новое приглашение после
минутного ограничения. Список `requests` содержит активные, отклонённые и истёкшие заявки; `requests
clear` скрывает отклонённые и истёкшие, сохраняя checkpoints защиты от повторов и недоставленные
уведомления. Connected-заявки скрыты из списка; их состояние доступно через peers и requests status.
Неодобренная заявка по истечении 30 суток отклоняется автоматически. Controller проверяет сроки и
повторяет доставку уведомлений; при недоступном API состояние сохраняется до продолжения доставки. В
статусе `delivery_pending` означает, что удалённая сторона ещё не подтвердила результат.
`delivery_confirmed: true` записывается только после проверки подписанного ответа, связанного с ID
заявки и nonce исходящего сообщения. При потере ответа заявка сохраняется для повторной доставки, но
интерфейс не сообщает об успешном получении. Старые записи без `delivery_confirmed` читаются без
миграции; отсутствие поля означает, что подтверждение доставки неизвестно. Одобренное обеими
сторонами или частично применённое подключение сохраняется для восстановления после срока заявки.
Сервер, уже присутствующий в локальном allowlist, можно приглашать, принимать или отклонять:
локальная политика не заменяет согласование через API. Активная заявка или уже согласованное
подключение не допускают второго приглашения. После отказа можно создать новую заявку с новым ID,
соблюдая минутное ограничение. Checkpoints действующего подключения и незавершённого применения
сохраняются. Отмена согласования сохраняет ранее применённые и независимо добавленные записи. Их
удаляет только отдельная местная `federation remove`. Панель создаёт отдельный личный зашифрованный
чат для каждого явно добавленного администратора. Примите приглашение в Matrix-клиенте.
Администратор также может пригласить бота в личный зашифрованный чат; бот проверит список доступа и
текущие права перед вступлением.

## Административный Matrix-бот

Аккаунт `@admin-panel:example.org` обычный, отдельный от `@referral-bot:example.org`. Его
собственная сессия не имеет admin scope. Доступ оператора требует наличия в списке доступа панели и
действующих прав администратора. Защищённая host-служба проверяет актуальные серверные права через
MAS — источник прав при действующей native OAuth интеграции. Проверяется местный server_name,
активность, locked/deactivated и серверное admin право, включая повтор перед отложенным применением.
Power level комнаты не даёт разрешения. Недоступность проверки означает отказ. Управляющий сокет
допускает только выделенный UID 10003 и фиксированные операции. У бота нет Docker socket, host root
volume или произвольного shell. У HTTP API нет административного dispatcher.

Команды без слешей:

```text
помощь
серверы
проверить сервер example.net
добавить сервер example.net
удалить сервер example.net
пригласить сервер example.net
заявки
операции
подтвердить MB-0123456789abcdef0123456789abcdef
отклонить MB-0123456789abcdef0123456789abcdef
отменить MB-0123456789abcdef0123456789abcdef
повторить MB-0123456789abcdef0123456789abcdef
статус MB-0123456789abcdef0123456789abcdef
продолжить изменение федерации
откатить изменение федерации
```

В личном чате бот присваивает заявке постоянный короткий номер и показывает его
в подтверждении и результате операции. Списки показываются по 20 заявок;
команды перехода указаны под списком, например `заявки входящие 2`.
Номера сохраняются при смене страницы. Даты заявок выводятся в МСК. Устаревшие
команды и повторное приглашение при активной заявке отклоняются до предложения
подтверждения; перед выполнением состояние проверяется снова. Команды очистки
отклонённых заявок в меню бота нет; CLI `requests clear` остаётся доступной.

Получение заявки и её одобрение, отказ или отмена приходят каждому администратору
в его личный зашифрованный чат. Недоступный чат не блокирует остальных получателей;
доставка в него повторяется отдельно. После принятия команды бот сообщает действие
и номер заявки, затем присылает итог; технический ID очереди не заменяет результат.
История уведомлений читается страницами ограниченного размера, сохраняя решения
по завершённым заявкам и отметки доставки отдельно для каждого администратора.
При обновлении старые общие отметки доставки сохраняются, но не определяют
получателя: возможно однократное повторное уведомление каждому администратору.
Дальнейшие повторы подавляются отдельной отметкой для этого администратора;
заявки и checkpoints согласования сохраняются.

Команды продолжения и отката предлагаются только при незавершённом изменении
местной политики. Они не восстанавливают сервер из резервной копии.

Собственные сообщения, edits и повторные события не выполняют повторное изменение. После сбоя используйте явный retry/recovery; replay исходного сообщения не является retry.
Шифрование использует существующий matrix-bot-sdk/Rust crypto SQLite и сохранённое устройство. Сессия/crypto store не заменяются при запуске.
Приглашения обрабатываются самим ботом. Сохранённая настройка `FEDERATION_AUTO_ACCEPT` в `settings/policy.env` управляет автоприёмом приглашений от удалённых ботов; default **false**. Автоматика требует connected request, одобренного peer, точного согласованного bot MXID и присутствия server_name в локальном allowlist. Совпадения локального имени недостаточно. Настройка не меняет allowlist.

## HTTPS discovery и доверие

`GET https://example.org/.well-known/misbot` публично возвращает protocol, instance_id, server_name, bot_mxid, api_path, algorithm, public_key, key_id, request_ttl и capabilities. Не требует Matrix-соединения/allowlist. Поле request_ttl сообщает поддержку срока 30 суток; capabilities содержит `federation-invites`. Если старый удалённый runtime не объявляет эти возможности или поддерживает только семь суток, новое приглашение прекращается с `peer_upgrade_required`; обновите его Misbot перед созданием заявки. Ранее созданные семидневные заявки и их исходные deadlines сохраняются.
`POST https://example.org/_misbot/v1/exchange` принимает подписанные действия `invite`, `status`, `decision`, `rejected`, `cancelled`. Подтверждение местным оператором выполняется только через CLI/UI/бота; удалённый `decision` сообщает одобрение удалённой стороны.
Межсерверная отмена не удаляет локальную политику и не отменяет независимые заявки.

Misbot API по умолчанию включён. `sudo misbot federation api status` показывает настройку; `api disable` и `api enable` меняют её до следующего явного переключения. Состояние хранится с identity, переживает перезапуск, обновление и резервное восстановление. При выключении оба публичных маршрута возвращают HTTP 503 с `api_disabled`; исходящие обмены приостановлены. Локальные команды, просмотр заявок и запись отказа/отзыва доступны, Matrix-федерация и allowlist сохраняются. Это переключатель межсерверного API, а не Telegram-бота, MAS или Matrix API.

Каждая установка генерирует отдельный RSA-3072 private key. RSA/SHA256 подпись PKCS#1 v1.5 покрывает canonical JSON payload (sort_keys, ASCII escapes, без пробелов), включая method/path, sender/recipient и их instance IDs, timestamp ±300 s, random nonce и body. Ответ также подписан и связан с request nonce через reply_to. Общего встроенного секрета нет.
Первое discovery аутентифицируется обычным HTTPS для ровно заявленного server_name; ключ/instance ID закрепляются при одобренном подключении и внутри каждой заявки. Смена закреплённой identity требует отдельного административного решения; автоматической подмены нет.
Транспорт разрешает только фиксированные origin/path, порт 443, публичные IP. Все результаты DNS проверяются; соединение использует один из проверенных адресов без повторного DNS, TLS сохраняет исходное имя/SNI. Redirects не выполняются. Ключи, URLs или response bodies ошибок не записываются в operational logs.
Лимит тела/ответа 32 KiB, 30 запросов/мин на локальный listener; это отдельное ограничение от создания приглашений раз в минуту. Общий deadline сетевого обмена — 10 s, включая DNS, соединение, TLS, заголовки и тело ответа; медленная по частям передача не продлевает его. Одновременно допускается не более четырёх незавершённых DNS lookup; при их занятости возвращается `dns_busy`. Nonce хранится 10 min. Входящий запрос проходит проверку формы до discovery. Discovery и проверка подписи выполняются без общей блокировки установки и mutex контроллера; перед записью повторно проверяются состояние установки, API, локальная identity, закреплённая identity peer, срок и nonce.

Лимит сохранённых заявок — 1000, событий мутаций — 100000, операций бота — 1000. Просмотр статуса, списков и проверка сервера не добавляют события; уже сохранённые события чтения остаются для совместимости защиты от повторов. Скрытие истории не удаляет checkpoints заявок и событий. При исчерпании количества новые записи отклоняются, а просмотр, discovery и локальный recovery через CLI без event ID остаются доступны. Автоматическое удаление или безопасная ротация истории пока не реализованы; перед планированием новых операций нужна операторская оценка приватной копии. Не удаляйте event IDs или заявки вручную: это снимает защиту от повторного применения.

Format-1 `state.json` читается отдельным приватным хранилищем с единым пределом чтения и записи 32
MiB. Прежние файлы, включая выросшие за 128 KiB, читаются без миграции и без смены identity. Размер
UTF-8 и лимиты коллекций проверяются **до** атомарной публикации. Ошибка `federation_state_capacity`
сохраняет прежний читаемый checkpoint; неизвестный формат или небезопасные права не исправляются
автоматически. Ограничение байтов также может остановить рост существующей операции: сохраните
checkpoint и проверьте его приватно; увеличение лимита или удаление защиты от повторов не является
штатным recovery. Нужны OpenSSL (штатная зависимость установщика), синхронизированное время и
рабочий HTTPS сертификат. При signature/expired_request проверьте время/NTP, protocol и публичный
ключ peer, затем requests retry. При peer_identity_changed не обходите pin: выясните
восстановление/замену удалённой установки. HTTP-маршруты Matrix/OAuth сохраняются; API расположен на
основном домене до общего redirect, новый поддомен не требуется.

## Постоянное состояние и восстановление

* `data/federation/identity.pem`, `state.json` — private key, instance identity, peers, заявки, nonce/event checkpoints (root 0700/0600).
* `config/federation-bot.json`, `secrets/federation-session.json`, `data/referral-control/federation-session.json` — приватная обычная bot session.
* `data/federation-bot/` — отдельное устройство, sync state, crypto SQLite, cross signing (UID 10003, 0700).
* `stages/federation/ID`, `federation-transition.json` — приватное локальное recovery.
* `run/federation/` — временные Unix sockets, в backup не входят.

Панель хранит cross-signing в `data/federation-bot/cross-signing.json`,
серверный помощник — в `data/federation-bot/welcome/cross-signing.json`.
Аккаунты используют разные ключи. Повторный запуск сохраняет оба файла,
сессии и устройства; чужая или несовпадающая identity отклоняется.
При незавершённой первой установке сбой готовности ботов останавливает запуск
до публикации HTTPS и веб-служб. После исправления причины продолжите установку
тем же мастером и каталогом, сохраняя данные и checkpoints.

Обычная согласованная копия включает это состояние; бот останавливается вместе с писателями,
API/backend сериализуются общей блокировкой. Проверка восстановления проверяет
identity/session/crypto files. Staged restore не запускает ни бот, ни API до `backup activate
--confirm source-stopped`; freeze останавливает host controller. Systemd unit привязан к домену и
конкретному каталогу, чужое назначение не перезаписывается. Перед активацией на другой машине
необходимо остановить источник: распределённого lease между независимыми VPS нет, это существующий
обязательный activation gate. При переносе в другой каталог на одной машине выполните
`sudo bash /путь/источника/install.sh down`: команда освобождает свой Compose slot и удаляет только свой
остановленный controller unit, сохраняя данные и identity. Обычный `stop` сохраняет привязку unit к
источнику. В SSH-меню раздел **Связь с другими серверами** вызывает те же команды. Help и version
работают без секретов/Docker.

## Вымышленный пример обмена

```json
{"payload":{"protocol":1,"sender":"a.example.org","instance_id":"0123456789abcdef0123456789abcdef","recipient":"b.example.org","recipient_instance":"abcdef0123456789abcdef0123456789","timestamp":1893456000,"nonce":"1234567890abcdef1234567890abcdef","method":"POST","path":"/_misbot/v1/exchange","body":{"action":"invite","request_id":"MB-0123456789abcdef0123456789abcdef","expires_at":1896048000,"approved":true,"applied":false}},"signature":"BASE64_RSA_SIGNATURE"}
```

Подпись примера — placeholder, а не действующий запрос. Получатель отвечает такой же подписанной оболочкой: body содержит request_id, reply_to (nonce запроса), state, approved и applied.
Реальный обмен выполняет `misbot federation invite`, оператор не переносит private key между серверами.

Используемые механизмы: [Synapse server admin API](https://element-hq.github.io/synapse/latest/usage/administration/admin_api/user_admin_api.html),
[SDK crypto store](https://github.com/turt2live/matrix-bot-sdk/blob/main/examples/encryption_bot.ts).

## Изменение через бота и остановка для копии

Изменение через бота сначала получает сохранённый operation ID `FO-` плюс 32 hex символа и статус queued. Узкая служба независимо выполняет фиксированную операцию после повторной проверки прав. Копия может остановить и перезапустить сам бот; команда от этого не теряется. Результат сохраняется и приходит уведомлением после его запуска.
`операции` в боте или `sudo misbot federation operations` показывает queued/running/complete/failed/interrupted. Перезапуск controller не запускает повторно running операцию: сначала её checkpoint и явный recovery/retry. До предложения подтверждения и до постановки в очередь служба проверяет актуальное состояние заявки; перед исполнением повторяет проверку под блокировкой. Отклонённую, отменённую или уже обрабатываемую заявку нельзя подтвердить повторно. Очередь сохраняет единственную незавершённую операцию для заявки. Duplicate Matrix event сохраняет тот же operation ID, не создавая вторую работу. Операции CLI выполняются синхронно.


Административная панель разрешает команды нескольким явно добавленным местным
аккаунтам. Список доступа и действующие права MAS проверяются независимо: одного
совпадения MXID или членства в чате недостаточно. У каждого администратора отдельный
личный зашифрованный чат; удалённый HTTP API не даёт административного доступа.
Управление списком и полные ограничения: [панель администратора](admin-panel.md#личный-аккаунт-администратора).
