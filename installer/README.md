# Misbot 1.1.0 — Matrix на чистом сервере

Комплект подготовлен для проверки владельцем. Лицензия исходников пока не выбрана;
публичный релиз не опубликован. До публикации остаются открытыми полный проход
установки с публичным HTTPS, браузерный вход и регистрация, восстановление
зашифрованной внешней копии и полный сценарий обновления с recovery.

Этот комплект устанавливает Synapse, PostgreSQL, Matrix Authentication Service (MAS), Element Web, Element Admin, LiveKit, сервис авторизации MatrixRTC, Caddy, HAProxy и трёх Matrix-ботов: приветственного, реферального с отдельным сервисом приглашений и административного с узкой host-службой федерации/API. Вход в Element X — по короткому основному домену; Google, Telegram и пароль обслуживает MAS. Шифрование включено по умолчанию при создании комнат совместимыми клиентами. Звонки используют MatrixRTC и TURN.

Все внутренние пароли, общие токены, ключ RSA MAS и пароль первоначального администратора создаются автоматически. При первом запуске MAS генерирует параметры хранения паролей, Synapse — свой ключ подписи. Повторный запуск сохраняет эти значения. Комплект не содержит реквизитов действующего сервера.

Первоначальный администратор создаётся через внутренний API MAS; пароль передаётся
через stdin и тело запроса, без секретов в аргументах процессов. Если создание
прервалось, выполните `sudo misbot start` повторно:
установщик использует сохранённый пароль и проверяет принадлежность частично
созданной учётной записи. Чужую, заблокированную или отключённую учётную запись
он не перезаписывает. Не удаляйте данные и каталог `secrets` для повторной попытки.

Маршрут от чистой машины до обновления, восстановления, переноса и отключения
показан в [жизненном цикле](lifecycle.md). Варианты локального/внешнего хранения,
границы реализации и план их проверки — в [архитектуре](architecture.md).
Команды подключения S3 и восстановления после сбоя переноса — в
[инструкции хранилищ](storage.md); ограничения и статус проверок указаны там явно.
Перенос уже заполненной локальной PostgreSQL во внешнюю выполняется отдельной
операцией `database-external`, с остановкой writers, копией и recovery journal;
поддерживаемые варианты и команды продолжения приведены в том же документе.
Отдельная смена пароля администратора и восстановление после прерывания описаны
в [инструкции credentials](credentials.md).
Там же описаны `database-password` и `database-password-recover` для смены
паролей Synapse/MAS в установленной локальной или внешней PostgreSQL.
`s3-credentials PRIVATE_S3_ENV` меняет только ключи доступа к прежним
S3-медиа с backup/recovery; условия, проверка и отдельные credentials внешних
копий приведены в [credentials.md](credentials.md#ключи-доступа-к-s3-медиа).
Для восстановления старых копий используйте актуальный установщик: обработка
одноразовых ключей до запуска описана в [backup.md](backup.md#одноразовые-ключи-после-восстановления).
При восстановлении в другой каталог на том же тестовом VPS сначала освободите
Compose-проект командой `sudo bash /путь/исходной/установки/install.sh down`.
Она сохраняет данные, ключи и checkpoints. `stop` оставляет контейнеры и сеть
привязанными к прежнему каталогу; удаление установки и выключение машины —
отдельные операции из [жизненного цикла](lifecycle.md).
Версионное хранение секретных файлов в Vault KV v2, локальный кэш при отказе
сервиса и AppRole описаны в [инструкции Vault](vault.md).
Основная конфигурация — локальная PostgreSQL, локальные медиа или S3 и защищённые
внешние резервные копии. Архив содержит runtime и пользовательские инструкции.
Тесты и сборочные инструменты доступны разработчикам в исходниках проекта.

Основной командный интерфейс и диагностика S3: [команда misbot](cli.md).

## 1. Что подготовить

Нужен отдельный чистый VPS с публичным IPv4, Linux **amd64**, systemd, доступом root/sudo и свободными портами из таблицы ниже. Автоматическая установка Docker поддерживает Ubuntu 24.04/26.04 и Debian 12/13. Рекомендуем Ubuntu 24.04. Практический минимум для небольшой нагрузки — **2 vCPU, 2 ГиБ RAM, SSD 20 ГиБ**, минимум 10 ГиБ свободного диска до скачивания образов и 3 ГиБ после него. Для роста и звонков разумный ориентир — 4 ГиБ RAM и SSD 40 ГиБ. Это оценка по составу и лимитам служб, а не нагрузочный benchmark; медиа и обслуживание требуют дополнительного места. При RAM меньше 2 ГБ и отсутствии достаточного swap установщик создаст файл swap размером 1 ГБ.

Нужны права управления DNS выбранного домена и, для соответствующих способов входа, приложения OAuth в Google Cloud и BotFather. Исходящие HTTPS/DNS-запросы сервера должны быть разрешены. Если Telegram недоступен напрямую, нужен постоянный SOCKS5-прокси.

Одна установка занимает весь указанный каталог и Compose-проект `matrix-stack`. Установщик откажется использовать чужой непустой каталог или Compose-проект из другого каталога. Он устанавливает Docker из официального репозитория, добавляет собственный файл sysctl для UDP-буферов, службы systemd для обновления TURN-сертификата и при необходимости swap. Существующие конфликтующие пакеты Docker автоматически не удаляет.

Далее `example.org` — **ваш** основной домен. Выберите его окончательно: он станет частью Matrix ID `@имя:example.org`. Изменение домена готовой установки или подмена его в старой базе не поддерживаются.

В `init` вводите только имя домена, без `https://`, пути или порта. Ошибка такого ввода проверяется до создания каталога: исправьте имя и повторите
ту же команду. Чужой непустой каталог по-прежнему защищён от перезаписи.
Если прежний комплект уже оставил непустой каталог без `installation.json`,
сохраните его и выберите новый: например,
`sudo bash /root/matrix-installer/install.sh init example.org /opt/matrix-stack-new`.
Далее выполняйте команды из `/opt/matrix-stack-new/install.sh`, подставляя этот
путь вместо `/opt/matrix-stack`. Не удаляйте каталог с неизвестными данными
для обхода отказа.

## 2. DNS и сетевые порты

Создайте семь записей **A** с одним публичным IPv4 VPS:

По умолчанию MAS использует `mas.<DOMAIN>`. Для другого существующего имени
задайте `MAS_DOMAIN` в `settings/server.env` до первого запуска, например
`MAS_DOMAIN=auth.example.net`. Используйте его вместо `mas.example.org` в DNS
и OAuth redirect URI/origin. Совместный hostname с Matrix API поддерживается;
issuer действующей установки изменять нельзя. Подробности — в
[конфигурации](configuration.md#отдельный-домен-mas).

| Имя | Назначение |
|---|---|
| `example.org` | Короткий адрес Element X, server_name, обнаружение сервисов; браузер открывает локальный лендинг по умолчанию |
| `matrix.example.org` | Synapse: Matrix API, вложения, федерация |
| `mas.example.org` | MAS: OAuth, вход и управление аккаунтом |
| `admin.example.org` | Element Admin |
| `web.example.org` | Element Web |
| `rtc.example.org` | Авторизация звонков и WebSocket LiveKit |
| `turn.example.org` | TURN для звонков через ограниченные сети |

Для корня DNS-панели обычно используют имя `@`, для остальных — `matrix`, `mas` и т. Д. Удалите AAAA для этих семи имён: комплект рассчитан на IPv4. Используйте режим DNS only, без HTTP/CDN-прокси. Если есть ограничивающие CAA, разрешите `letsencrypt.org`. Дождитесь обновления DNS. Домены `element.example.org` и `live.example.org` не нужны.

`preflight` проверяет CAA для каждого имени с наследованием от
родителей и обработкой ответа CNAME. Отсутствие CAA не ограничивает выпуск;
для ограничивающей политики поддержана `CAA 0 issue "letsencrypt.org"`.
Неизвестный critical tag, другой issuer, запрет выпуска и ограничивающие issuer
parameters приводят к отказу с именем и следующей командой. Политика только
`issuewild` не ограничивает обычные сертификаты этих семи имён. Сложные параметры
ACME account/validation требуют отдельного согласования политики и пока не
подтверждаются установщиком. Проверка следует [RFC 8659](https://www.rfc-editor.org/rfc/rfc8659.html#section-3).
Ошибку DNS-запроса не считайте отсутствием CAA: восстановите resolver и повторите.
`up` устанавливает `dnsutils`; если запускаете `preflight` до установки зависимостей,
при отсутствии `dig` выполните `sudo apt-get install dnsutils` и повторите команду.

Разрешите в сетевом экране провайдера и на сервере:

| Протокол и порт | Назначение |
|---|---|
| Ваш TCP-порт SSH | Администрирование; сохраните действующее правило |
| TCP 80 | HTTP и выпуск сертификатов Let's Encrypt |
| TCP 443 | HTTPS всех сайтов, федерация через discovery, TURN/TLS через SNI |
| TCP 7881 | Резервный транспорт WebRTC |
| UDP 7882 | Основной транспорт WebRTC, UDP mux |
| UDP 3478 | TURN/UDP |

Порты PostgreSQL 5432, Synapse 8008, MAS 8080 и LiveKit API 7880 наружу не публикуются. TCP 8448 не нужен: federation discovery указывает HTTPS 443. Диапазон UDP 50000–60000 не нужен при настроенном mux 7882. Комплект не включает UFW и не меняет правила вашего SSH. Учтите, что публикация портов Docker взаимодействует с iptables и может обходить обычные правила UFW; входящий доступ ограничивайте также экраном провайдера. Официальные источники: [Docker и firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/), [порты LiveKit](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

## 3. Загрузка и создание файлов

Если используете исходники этого репозитория, сначала соберите архив из его корня командой `python3 installer/build.py`. Архив создаётся как `dist/matrix-installer.tar.gz` и не хранится в Git. Сборка берёт код ботов непосредственно из `bots/telegram/` и `bots/matrix-referral/`; в архиве создаются нужные каталоги, а копии исходников в Git не хранятся.

Передайте `matrix-installer.tar.gz` и созданный рядом `matrix-installer.tar.gz.sha256` на сервер через SCP. Сверьте checksum с доверенным значением владельца; затем из каталога с файлами:

```bash
sha256sum -c matrix-installer.tar.gz.sha256
sudo install -d -m 700 /root/misbot-setup
sudo tar -xzf matrix-installer.tar.gz -C /root/misbot-setup
sudo sh -c 'cd /root/misbot-setup/matrix-installer && sha256sum -c SHA256SUMS'
sudo python3 /root/misbot-setup/matrix-installer/misbot.py ui
```

Выполняйте команду в SSH-терминале Linux. До установки используется `python3 misbot.py ui` из распакованного комплекта; после init системная команда `misbot` доступна из любого каталога. Если отсутствуют зависимости DNS: `sudo apt-get update`, затем `sudo apt-get install -y python3 python3-yaml dnsutils iproute2`. Мастер проверяет систему, DNS/CAA и порты, предлагает локальные медиа или проверку S3, необязательные способы входа и внешние копии. Enter сохраняет default или существующий секрет. Команды ввода: `назад`, `отмена`, `сохранить и выйти`.

Для другого каталога: `sudo python3 misbot.py --directory '/opt/My Matrix' ui`. После возвращения по SSH: `sudo misbot ui`. Без TTY команда без аргументов показывает help; явный `ui` возвращает отказ с подсказкой `ssh -t`. Пароли вводятся без эха. Ключи и пароль администратора создаёт backend; повтор их сохраняет.

В конце мастер показывает `@matrix-admin:example.org`, адрес входа и отдельный токен на одну обычную регистрацию, default 7 дней. Токен вводят в форме регистрации, не в URL. Просмотр только в терминале root: `sudo misbot credentials admin show` и `sudo misbot users invitation show`. Статус без токена: `sudo misbot users invitation status`. Если MAS ещё не готов: `sudo misbot users invitation ensure`; переустановка не нужна.

Ручной путь и полная таблица полей: [конфигурация](configuration.md). Основной файл `settings/server.env` содержит домен, публичный IP, email и режимы хранения. Условные файлы создаются только для выбранных ресурсов. `settings/policy.env` содержит параметры регистрации и федерации; отсутствующий файл использует документированные defaults. Существующий `settings.env` поддерживается до явной команды `sudo misbot config migrate`.

Основной домен показывает локальный [лендинг](homepage.md). «Войти» и «Зарегистрироваться» открывают штатный клиент/MAS; приглашение вводится в форме, не в URL. Настройки сайта — необязательный `settings/site.env`, раздел UI «главная страница» и `sudo misbot homepage help`. `sudo misbot homepage apply --mode element` выбирает Element; `--mode external --url https://community.example.net/` — временную внешнюю переадресацию, `--mode landing` возвращает страницу. Проверка маршрутов не заменяет настоящий браузерный вход.

После ручного редактирования: `sudo misbot config validate`, затем `sudo misbot config apply` и `sudo misbot check`. `config apply` создаёт и проверяет согласованную копию перед применением. Не редактируйте внутренние generated configs, пароли, DOMAIN/server_name или credentials действующего ресурса: используйте его отдельную backend-операцию. Env читается буквально, никогда не выполняется через `source`.

## 4. Google

В Google Cloud настройте OAuth consent screen и создайте OAuth client типа **Web application**. Добавьте в **Authorized redirect URIs** точный адрес:

```text
https://mas.example.org/upstream/callback/01K5WZ00000000000000000001
```

Впишите Client ID и Client Secret в `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`. Если интерфейс просит Authorized JavaScript origins, используйте `https://mas.example.org`, без пути. Вход здесь использует серверный redirect flow. В режиме Testing разрешите нужные Google-аккаунты как test users; для остальных пользователей настройте публикацию consent screen по правилам Google. Домен, приложение и доступные пользователи выбираются владельцем — установщик не может сделать это за него. [Документация Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

## 5. Telegram

В BotFather создайте или выберите своего бота и включите **OpenID Connect Login**. Используйте выданные для этого раздела Client ID и Client Secret, а не токен бота или реквизиты приложения Telegram API.

В **Redirect URIs** добавьте:

```text
https://mas.example.org/upstream/callback/01K5WZ00000000000000000002
```

В **Trusted Origins** добавьте:

```text
https://mas.example.org
```

Впишите `TELEGRAM_CLIENT_ID` и `TELEGRAM_CLIENT_SECRET` в env. Если нужен прокси, заполните:

```dotenv
SOCKS5_CONFIG=socks5://username:password@proxy.example.net:1080
```

Спецсимволы в имени и пароле прокси кодируйте как URL (`@` → `%40`, `:` → `%3A`, `%` → `%25`). Прокси должен работать постоянно. Генератор включает удалённое DNS-разрешение SOCKS5; прокси используется MAS для Telegram, а Google и внутренние сервисы исключены через `NO_PROXY`. Это не прокси для медиа/звонков.

Для установленной версии MAS используется официальный JWKS Telegram с параметром `?format=json`, устраняющим наблюдавшуюся ошибку декодирования ответа. Проверка подписи токенов остаётся включённой. [Документация Telegram OIDC](https://core.telegram.org/bots/telegram-login).

Вход через разные провайдеры сам по себе может создать разные Matrix-аккаунты. Чтобы добавить свободную Telegram-идентичность к существующему аккаунту Google, сначала войдите через Google в MAS, затем **в том же браузере** откройте:

```text
https://mas.example.org/upstream/authorize/01K5WZ00000000000000000002
```

Подтвердите связывание. Уже связанная с другим, в том числе удалённым, аккаунтом идентичность автоматически не переносится. Удаление Matrix-аккаунта не гарантирует освобождения его OAuth-привязки или Matrix ID.

## 6. Запуск и проверка

После заполнения DNS, сетевых правил и env:

```bash
sudo misbot start
sudo misbot status
sudo misbot check
```

Перед `up` можно отдельно выполнить `sudo misbot config preflight`.
Успех — `{"check": "preflight", "passed": true, "hosts": 7}`. Эта команда читает
настройки и проверяет систему/DNS/сети/порты/прокси, не запускает Matrix и не
меняет его данные. `up` выполняет её автоматически до загрузки образов. Для
первой загрузки требуется 10 ГиБ свободно; при уже закэшированных образах и
Повторных запусках — не менее 3 ГиБ. Оставляйте дополнительное место под копии.
При несовпадении DNS сообщение называет имя, ожидаемый A и наблюдаемый адрес.
Исправьте запись в DNS-панели, дождитесь истечения кэша, повторите `preflight`,
затем `up`. Проверка resolver VPS не доказывает готовность всех внешних кэшей.
При конфликте порта используйте `sudo ss -lntup`; разрешите конфликт службы
перед повтором, сохранив SSH. При ошибке SOCKS5 исправьте реквизиты приватно или
отключите необязательный Telegram, очистив оба его поля; данные Matrix сохраните.

Первый запуск скачивает девять закреплённых образов и собирает два образа бота из включённых исходников и закреплённых зависимостей. Он проверяет конфигурации, создаёт обе базы, администратора, аккаунт и устройство бота, сертификаты и запускает одиннадцать контейнеров. Это может занять несколько минут. LiveKit запускается после выпуска TURN-сертификата. При ошибке исправьте причину и повторите `up`: существующие секреты и данные сохраняются. Установщик не отключает TLS-проверки для обхода проблем DNS или сертификатов.

Запись `waiting_for_service` показывает службу и максимальное время её ожидания:
обычно 120 секунд, для выпуска TURN-сертификата — 300. Это не общий предел
установки: загрузка и сборка образов могут идти дольше. При таймауте сообщение
содержит точную команду просмотра журналов и повторного `up`. Просматривайте
журналы приватно. Успех — запись `installation_running`, код завершения 0,
работающие контейнеры в `status` и успешный `check`. Если в старом комплекте
бот сообщал `ERR_INVALID_PACKAGE_CONFIG`/`permission denied` для `/app/package.json`,
примените исправленный проверенный архив командой `install.sh update` из нового
распакованного комплекта, указав каталог существующей установки; сохраните его
данные и секреты. Сборка назначает UID бота владельцем его исходников.

При отказе S3 перед запуском сохраняйте данные и конфигурацию. Исправьте доступ
к хранилищу и повторите указанную в сообщении команду. Это `up` для
обычного запуска или `database-recover` для незавершённого переноса БД.
Переход к локальному хранению через `media-local` предлагается только до
первого принятого запуска S3; действующее хранилище так не отключается.
Порядок продолжения переноса — в [storage.md](storage.md).

Откройте `https://web.example.org`. В Element X на телефоне укажите **example.org**. Проверьте вход Google/Telegram, создание зашифрованного чата, фото и звонок между двумя устройствами, желательно между Wi-Fi и мобильной сетью. Автоматический `check` проверяет доступность HTTP, discovery, OAuth metadata, TURN/TLS и состояние контейнеров; он не имитирует подтверждение входа провайдером и реальный телефонный звонок.

Администратор — `@matrix-admin:example.org`. Его автоматически созданный пароль и адрес админки доступны root:

```bash
sudo cat /opt/matrix-stack/secrets/admin-access.json
```

Войдите на `https://admin.example.org` именно этой учёткой через вариант с логином и паролем. Обычная Google/Telegram-учётка не получает административные права автоматически. Пароль не выводится установщиком и не попадает в журнал этапов. Сохраните его в своём менеджере паролей.

После перезагрузки контейнеры запускает Docker. Сертификаты выпускает и обновляет Caddy; systemd path/timer перезапускает LiveKit при обновлении пары TURN-сертификат/ключ. Краткий перерыв звонков при таком перезапуске возможен.

Обновление TURN-сертификата перезапускает только работающий LiveKit.
После сознательной остановки или удаления контейнера выдаётся
`turn_certificate_reload_deferred`; служба остаётся остановленной. Чтобы
вернуться к работе, выполните `install.sh up`, затем `check`: запуск использует
актуальные файлы сертификата. Это не команда окончательного отключения VPS.

### Реферальный бот

Аккаунт **`@referral-bot:example.org`**, имя **«Реферальный бот»**, создаётся автоматически при `up`. Откройте с ним личный зашифрованный чат в Element X. Для первого приглашения войдите первоначальным администратором; дальше кодами могут управлять все активные пользователи этой установки.

- `пригласить` — создать приглашение; сообщение можно целиком переслать другу.
- `пригласить Для Антона` — создать код с названием, которое видно только создателю.
- `токены` или `токены 20` — свои коды; отозванные и истёкшие неиспользованные скрыты, использованные остаются.
- `отозвать` — нумерованный список; ответьте номером. `ещё` продолжает список, `отмена` или `0` отменяют выбор. Выбор действует 15 минут. `отозвать ID` отзывает только собственный код.
- `помощь` — команды, аргументы, срок и лимит регистраций. Старые slash-команды показывают эту справку.

Отдельный `@federation-bot:example.org` управляет [федерацией и заявками Misbot](federation.md).
Команды: `серверы`, `проверить сервер example.net`, `пригласить сервер example.net`, `заявки`, `подтвердить MB-ID`, `помощь`.
Только текущие серверные администраторы собственного сервера имеют доступ; роль в комнате не подходит.
В SSH UI выберите раздел «федерация/бот/заявки», CLI: `sudo misbot federation help`.
Публичный discovery `/.well-known/misbot` и API `/_misbot/v1/exchange` работают до добавления peer в Matrix allowlist.

Коды выводятся моноширинным шрифтом, срок — в МСК. Бот принимает команды только в личных зашифрованных чатах с активными местными аккаунтами; кодами другого пользователя управлять нельзя. Он не управляет федерацией или пользователями. Telegram-бот в этот комплект не входит.

Устройство `MATRIX-REFERRAL-01` получает обычную клиентскую сессию без административных прав. Отдельный `referral-control` хранит служебные реквизиты MAS и предоставляет боту ограниченный Unix-сокет; ни один из двух контейнеров не публикует порт и не получает Docker socket. Устройство подписывается ключами cross-signing. Сессия, устройство, ключи, личные названия и диалоги сохраняются при повторном `up` и перезагрузке. При пропаже сохранённого состояния установщик требует восстановление из копии.

## 7. Файлы и обслуживание

[Краткая памятка и диагностика](administration.md) содержат команды, ожидаемые
результаты, действия при ошибках и ссылки на сложные операции.
[Пользователи и сеансы MAS](users.md) описывает блокировку, разблокировку и отзыв
сеансов с проверкой результата и действиями при ошибках.

| Путь относительно `/opt/matrix-stack` | Содержимое |
|---|---|
| `settings/` | Пользовательский набор формата 2; см. configuration.md |
| `secrets/` | Внутренние пароли/токены и пароль администратора |
| `config/` | Сгенерированные приватные конфигурации, ключ MAS, параметры хранения паролей MAS |
| `public/` | Только публичные well-known и конфигурация Element Web |
| `compose.yaml` | Все контейнеры и ограничения ресурсов |
| `installation.json`, `images.lock.json`, `referral-images.lock.json` | Домен, состояние установки, точные образы и контрольные суммы исходников бота |
| `referral-bot/`, `referral-control/`, `referral.py` | Исходники и автоматическая настройка бота |
| `config/referral-bot.json` | Приватная обычная сессия бота, домен, устройство и условия приглашений |
| `data/referral-bot/` | Криптобаза, cross-signing keys, названия, диалоги и checkpoint |
| `data/referral-control/` | Приватный журнал создания аккаунта/сессии, база владения кодами и Unix-сокет |
| `data/` | Также PostgreSQL, Synapse/media/signing key, сертификаты Caddy |
| `stages/` | Краткие результаты этапов без паролей |
| `backups/` | Полные приватные копии |

Основной каталог закрыт от обычных пользователей. Отдельные конфигурационные файлы принадлежат UID контейнеров, чтобы сервисы могли их читать. Caddy получает только каталог `public`, не секретные конфигурации.

Команды:

```bash
# Сохранить копию перед изменением настроек
sudo misbot backup create
sudo nano /opt/matrix-stack/settings/server.env
# Проверить и применить с проверенной копией
sudo misbot config validate
sudo misbot config apply
# Только сгенерировать и проверить файлы, без перезапуска
sudo misbot config generate
# Остановить, сохранив данные
sudo misbot stop
```

`generate` уже меняет конфигурационные файлы на диске; перезапуск службы может применить их. Для диагностики контейнеров:

```bash
sudo docker compose --project-directory /opt/matrix-stack -f /opt/matrix-stack/compose.yaml logs --tail=100 mas synapse
```

Журналы приложений могут содержать личные данные и OAuth-параметры: просматривайте их приватно. Не удаляйте файлы в `secrets`, `config/mas-defaults.yaml`, ключи подписи или `data`: это не кэш. При обнаружении пропажи сохранённых ключей/базы установщик требует восстановление вместо молчаливого создания новой установки.

Операции изменения используют общую блокировку одной установки. При сообщении
`Another installer operation is running` проверьте `status`, дождитесь завершения
операции и повторите команду. Не удаляйте её lock-файл. Подробности аварийного
выхода и ручных Docker-команд — в [разделе о журналах и диагностике](administration.md#журналы-и-диагностика).

## 8. Резервная копия и восстановление

Полный состав копии, команды шифрования и внешнего S3, скачивание на новой машине,
ошибки и условия восстановления зашифрованной истории описаны в
[backup.md](backup.md). Проверяйте пригодность копии для своей установки отдельно.

```bash
sudo misbot backup create
sudo misbot backup verify
```

Копирование кратко останавливает работающие referral-bot/referral-control/Synapse/MAS/JWT, делает логические дампы обеих баз и копирует конфигурации, ключи, env, исходники, медиа и сертификаты. В копию включены сессия и устройство бота, криптобаза, cross-signing keys, названия, диалоги и база владения приглашениями. Затем запускаются только те из этих служб, которые работали до копирования. Архив лежит в `backups/`, ссылка `latest.tar.gz` указывает на последнюю копию. `restore-check` проверяет SHA256, согласованность сессии бота и целостность его SQLite-баз, восстанавливает дампы в две временные базы, затем удаляет их; рабочие базы не заменяет. Эта проверка не заменяет полный пробный запуск восстановления на отдельном VPS.

Копия содержит все внутренние секреты, но **не зашифрована**. Храните её вне VPS в защищённом хранилище; переносите по SSH и ограничивайте доступ. Команды шифрованной внешней копии и проверяемого systemd-расписания — в [backup.md](backup.md#регулярные-копии-через-systemd). Внешний recovery key и AppRole auth files сохраняйте отдельно по инструкции.

Если неудачная S3 выгрузка сообщает отказ очистки, выполните `backup-cleanup`
с исходным private env и catalog по [инструкции резервного копирования](backup.md).
Она запрашивает удаление только непроверенного объекта этой попытки, сохраняя
локальные данные и прежние проверенные копии.

Для восстановления установки с **локальной PostgreSQL** на пустой VPS с тем же
доменом используйте новый распакованный комплект. Приёмку восстановления выполняйте отдельно для своих данных и клиентов.

1. На исходном VPS выполните `backup`, `restore-check` и запишите SHA256 из строки
   `consistent_backup`. Передайте архив по SSH в закрытый каталог целевой машины.
   Контрольная сумма должна прийти с источника, а не вычисляться только после передачи.
2. На целевом VPS из каталога нового комплекта выполните команду ниже. Замените
   имя архива, `SHA256_С_ИСТОЧНИКА` и пример IPv4 реальными значениями. Каталог
   назначения должен быть пустым. `init` перед восстановлением не требуется.

```bash
sudo python3 misbot.py backup restore --archive /root/matrix-backup.tar.gz --sha256 'SHA256_С_ИСТОЧНИКА' --public-ip 203.0.113.20 --directory /opt/matrix-stack
```

Команда проверяет SHA256, пути и типы файлов в обоих архивах, комплект исходников
и состояние бота; восстанавливает числовых владельцев, роли и обе базы.
Ожидаются `restored_database` для Synapse и MAS, затем `restore_staged` с
`writers_disabled=true`. Работает только PostgreSQL; Synapse/MAS/бот не запускаются.
Ошибка контрольной суммы требует повторной передачи исходного архива.
При прерывании повторите **ту же команду с тем же архивом**: промежуточное состояние
сохранено в `restore-journal.json`. Проверенный архив копируется
в приватный `backups/` назначения; для этого нужно дополнительное место размером
с архив. До регистрации команды из распакованного комплекта выполните `sudo python3 misbot.py --directory /opt/matrix-stack backup verify` для
проверки обоих дампов во временных БД. Относительная `backups/latest.tar.gz`,
созданная restore, допускается при повторе; произвольные ссылки
и ссылки вне каталога резервных копий отклоняются. Частичный импорт сбрасывается только в этом
каталоге восстановления. Непустая действующая установка и другой архив отклоняются.

3. На источнике текущим установщиком выполните `sudo misbot backup move export`,
   затем `restore-check`. Успех — `migration_source_frozen` с путём финального
   архива; запись остаётся остановленной. S3 originals проверяются и
   отсутствующие локальные файлы докачиваются до архива. При отказе сохраняйте
   источник, проверьте status и повторите move-export после исправления ресурса.
   Подробный путь внешней защищённой копии и отмены — [backup.md](backup.md#финальная-копия-перед-переносом).
   После обрыва SSH или прерывания выполните `sudo misbot status`.
   вывод включает stopped containers, migration_frozen и точные
   next_actions; дождитесь завершения активной операции перед recovery.
   жёсткие ссылки, оставшиеся после аварийного завершения скачивания,
   записываются в архив как отдельные обычные файлы. Установщик не удаляет
   неизвестные scratch-файлы; symlink и специальные файлы в копируемых
   каталогах отклоняются без чтения внешних данных. Штатный временный
   `data/referral-control/bot-run/control.sock` не копируется: служба создаёт
   его при запуске; состояние управления сохраняется в SQLite и конфигурации.
   Восстановите финальную согласованную копию в новый пустой каталог.
   Две независимые пишущие установки недопустимы.
   Переключите семь A-записей на целевой IPv4, проверьте отсутствие AAAA и дождитесь
   обновления DNS. Затем из восстановленного каталога:

```bash
sudo python3 misbot.py --directory /opt/matrix-stack backup activate --confirm source-stopped
sudo misbot check
```

`source-stopped` — явное подтверждение администратора, что источник остановлен;
команда сама не управляет другой машиной. До успешного preflight запись остаётся
заблокированной. При ошибке активации целевой стек останавливается; исправьте
причину и повторите активацию. Проверка HTTP endpoints не заменяет вход пользователей,
исторические вложения, зашифрованные сообщения, федерацию и звонки.

Обычный `up` на staged-копии сообщает о запрещённых writers и следующей
операции `restore-activate source-stopped` до DNS/ресурсных проверок. Менять DNS
ради пробного восстановления не нужно. Для реального переключения сначала
остановите источник, выполните проверки копии, затем пройдите маршрут выше.

Если архив создан с внешней PostgreSQL, используйте явное
восстановление обеих БД в новую локальную PostgreSQL18:

```bash
sudo python3 misbot.py backup restore-local --archive /root/matrix-backup.tar.gz --sha256 'SHA256_С_ИСТОЧНИКА' --public-ip 203.0.113.20 --directory /opt/matrix-stack
```

Исходная внешняя БД при этом не подключается и не изменяется. Остальные проверки,
staged ограничения и порядок активации те же. При прерывании повторяйте именно
restore-local, не меняя архив/IP/назначение. Подробности и границы серверной
проверки — [backup.md](backup.md#внешняя-postgresql-восстановление-в-локальную).
Восстановление в другой внешний кластер остаётся неподдержанным.
Серверная копия не содержит ключей E2EE из клиентских устройств: для зашифрованной
истории пользователю нужны его проверенное устройство или ключ восстановления
и доступная резервная копия клиентских ключей.

Маркеры `referral_seeded`, `referral_provisioned`, `referral_crypto_initialized` сохраняйте. Восстанавливайте конфигурацию, сессию, устройство и все данные бота вместе с обеими базами. Не создавайте новое устройство поверх старого crypto store и не удаляйте ключи ради повторного запуска.

Восстановление сохраняет исходный `server_name`; прямой импорт базы другой установки с другим доменом сюда не предусмотрен. Импорт существующих Synapse/MAS требует отдельного плана, остановки источника и сохранения совместимых ключей/идентификаторов.

## 9. Версии и границы возможностей

первоначальные секреты, `homeserver.yaml` и `mas.yaml` записываются атомарно,
а новый MAS signing key публикуется только после успешного завершения RSA
генератора. После прерывания init сохраните каталог и повторите исходную
команду; busy означает ещё работающего потомка. Уже использованные ключи
автоматически не заменяются: исчезнувший ключ восстанавливают из копии.

Образы закреплены по SHA256 в `versions.json`, чтобы воспроизвести текущий сервер, а не получить неожиданное обновление `latest`:

| Сервис | Версия |
|---|---|
| Synapse | 1.162.0 |
| MAS | 1.25.1 |
| PostgreSQL | 18.6 |
| Element Web | 1.12.29 |
| Element Admin | 0.1.14 |
| LiveKit | 1.13.7 |
| lk-jwt-service | 0.7.0 |
| Caddy | 2.11.4-alpine |
| HAProxy | 3.4-alpine |
| Реферальный бот | 1.0.0; Node.js 24, matrix-bot-sdk 0.8.0, crypto SDK 0.4.0 |
| Сервис управления приглашениями | Python 3.14; зависимости закреплены в requirements.txt |

Базовые образы двух собственных сервисов также закреплены по digest в `versions.json`. После сборки Compose использует их неизменяемые image ID; результат и контрольные суммы исходников сохраняются в `referral-images.lock.json`.

Обновление версии — отдельная операция с копией и проверкой совместимости. Смена major PostgreSQL требует миграции, а не замены строки образа.

Element Web — официальный браузерный клиент; отдельный стабильный браузерный Element X в этот комплект не входит. Старый password login Synapse отключён; используется OAuth/MAS. Это ограничивает старые клиенты, но не является абсолютным запретом любого приложения с названием Classic, если оно поддерживает нужный OAuth. Подписи фотографий, альбомы и сжатие фото/видео зависят от возможностей/настроек клиента; сервер не перекодирует зашифрованные вложения. Ключ восстановления E2EE не заменяется входом Google/Telegram: сохраните его отдельно. Почтовый SMTP не настроен; восстановление локального пароля по email без настройки почты недоступно.

В исходниках проекта есть проверки генератора и создания бота, а также изолированный тест настоящих контейнеров: новые базы, OAuth/PKCE, административные разрешения, обновление токена, автоматическое создание обычного аккаунта бота, зашифрованные команды и ответы, выдача/отзыв кода, цепочка подписи устройства, сохранение ключей после перезапуска и повторной генерации, проверка резервной копии. Они не запускают весь публичный стек на вымышленном домене и не проверяют установку пакетов на каждой поддерживаемой ОС. Проверку DNS/ACME и входа с телефонов завершайте на своём новом сервере по разделу 6.

## 10. Обновление

Версия продукта/сервера — **1.1.0**; `misbot version` выводит `Misbot 1.1.0`. Проверка GitHub Release: `sudo misbot update check`; загрузка готового проверенного комплекта и применение: `sudo misbot update latest`. Панель поддерживает команду `обновить` с подтверждением и устойчивым результатом. [Панель и уведомления](admin-panel.md).
Она хранится в `release.json`; версии и digest компонентов — в `versions.json`.
Версия формата состояния — `config_format_version=1` в
`installation.json` (отсутствующее поле прежнего комплекта означает формат 1).
Старую Docker-сеть без метки каталога установщик
заменяет после проверки владельцев всех подключённых контейнеров: временно
останавливает свой стек, сохраняет файлы БД/медиа/ключей и запускает службы снова.
Это требует перерыва; при прерывании update используйте update-recover, при
прерывании обычного up — повторите up. Не удаляйте сеть или данные вручную.
Чужой контейнер или отсутствие свидетельства владения приводят к отказу.

Поддерживается обновление исходников совместимого переносимого комплекта с
неизменными digest компонентов и точный переход Synapse 1.161.0 → 1.162.0
при прежних закреплённых образах остальных компонентов. Установка должна иметь
исходники и `SHA256SUMS`. Проверка ограниченного пути включает полное versions.json,
фактическую schema94/compat84, завершение background updates и runtime version.
Для старых установок без manifest нужен отдельный план импорта; ручная выборочная
замена файлов не является поддерживаемым путём обновления.

На VPS распакуйте новый доверенный комплект в отдельный каталог, проверьте его
`sha256sum -c SHA256SUMS` и из этого каталога выполните:

```bash
sudo misbot update apply --directory /opt/matrix-stack --source /root/matrix-installer
sudo misbot check
```

Перед заменой исходников кандидат создаёт полную согласованную копию и проверяет
восстановление обеих баз; при отказе этой проверки исходники не заменяются.
до копии проверяются свободное место и размер обеих БД/файлов с запасом
для архива и перезапуска. При отказе расширьте диск либо удалите посторонние
файлы, сохранив Matrix данные, ключи и проверенные копии, затем повторите update.
Ожидается `release_applied` с версией кандидата. Ключи, `server_name`, реквизиты
и данные сохраняются. При провале запуска возвращаются прежние исходники и
конфигурации; результат повторного запуска указан как `rollback healthy`.
Приватные журналы находятся в `stages/updates/…/`.

прерывание обновления обрабатывается с откатом; перед заменой
исходников сохраняется приватный `update-journal.json`. После SIGKILL или
неуспешного отката обычные изменения блокируются до восстановления.
Используйте доверенный распакованный комплект: файл install.sh внутри
установки мог оказаться частично заменён.

```bash
sudo misbot update recover --directory /opt/matrix-stack --source /root/matrix-installer
sudo misbot check
```

Ожидается `update_recovered` прежней версии и `healthy True`. После этого
можно повторить update из нового комплекта. Не удаляйте journal или checkpoint.
Если восстановленные службы не запускаются, исправьте указанную причину и
Повторите update-recover. Во время recovery данные и прежние ключи сохраняются.
Для обновления исходников с теми же компонентами эта операция не откатывает
схему БД. SIGTERM/SIGINT передаются внутренним backup/up для завершения cleanup.
Recovery выполняйте через доверенный распакованный комплект, даже если
прежние установленные скрипты не знают о pending journal.

Для существующего обычного пользователя используйте `user-password PRIVATE_JSON`
и `user-password-recover`: подготовка файла, ожидаемый результат и восстановление
описаны в [users.md](users.md). Пароль в аргумент shell не передаётся; для
первоначального matrix-admin остаётся отдельная [смена пароля администратора](credentials.md#пароль-первоначального-администратора).

Произвольная смена digest, неизвестный формат конфигурации и понижение версии отклоняются.
Автоматический возврат исходников не откатывает схему БД: для обновлений компонентов,
изменяющих схему, нужны полный архив до обновления и проверенное восстановление
на отдельной машине. Допущенная пара161→162 имеет совместимую схему; перед
возвратом161 установщик останавливает writers и проверяет её фактическое состояние.
Новые данные не заменяются pre-update дампом. При неизвестной схеме или pending
background updates прежний runtime не запускается: сохраните journal/данные,
исправьте указанную причину либо восстановите полный архив в пустом каталоге
совместимым доверенным комплектом по [backup.md](backup.md). Этот ограниченный путь
не является поддержкой произвольного schema rollback или major PostgreSQL.
После успешного component update ожидается `component_applied synapse 1.161.0 1.162.0`.
Наблюдаемая runtime version:

```bash
sudo docker compose --project-directory /opt/matrix-stack exec -T synapse python -c 'from synapse import __version__; print(__version__)'
```

Ожидается `1.162.0`. Повтор update того же набора образов является обычным
Обновлением исходников. При S3 пересобирается образ с прежним storage provider1.7.0
и новым базовым Synapse; доступ к registry и свободное место нужны до успеха.
Проверка обновления компонентов требует отдельной проверки фактической схемы
и работающих служб; успех обновления исходников её не заменяет.


## 11. Панель, приветствия и полное удаление

[Панель администратора](admin-panel.md): новый тег `@admin-panel`, сохранение
старого тега при обновлении, доступ только владельцу, уведомления и проверка версий,
обновление из GitHub Releases, приветствие `@server-guide`, рассылки с подтверждением
и статистика. В меню бота отсутствуют операции копирования и переноса данных.

`sudo misbot remove` работает после `init`, при незавершённой установке и на
работающем portable-сервере. В интерактивном терминале выберите категории локальных
данных, каждый S3 prefix, внешние installer-owned БД и Vault. Затем подтвердите
итоговый список и точную фразу с доменом. Перед финальным подтверждением данные
не удаляются. S3 очищается вместе с версиями, delete markers и незавершёнными
uploads в выбранном prefix; bucket и другие prefixes сохраняются. Для отдельного
профиля копий можно передать `--backup-config /root/misbot-backup-s3.env`.

Удаление сначала останавливает writers/units, затем очищает выбранные внешние
ресурсы, контейнеры и локальные данные. Отказ удалённого провайдера сохраняет
локальные credentials и journal; повтор той же команды продолжает прежний план
после нового подтверждения. Удаление не превращает отсутствующий доступ в успех.
Исходники утилиты и системная команда остаются. После полного удаления:
`sudo misbot config init --domain example.org`, затем `sudo misbot ui`.
При частичном выборе сохранённые файлы остаются, но запуск сервера блокируется;
для новой установки сначала завершите полное удаление.

Выгрузки и секретные файлы, вручную сохранённые вне установки, копии на других
Matrix-серверах и устройствах пользователей не входят в локальную область удаления.
Удаление не удаляет VPS, домен, аккаунт у S3-провайдера или Docker как системный пакет.
