# Резервные копии и восстановление

Команды выполняются по SSH на VPS. Копия содержит пароли, ключи и персональные
данные; не пересылайте её в чат и не добавляйте в Git. Архив установщика из `dist`
содержит исходники и не является копией установленного сервера.

## Локальная согласованная копия

```bash
sudo misbot backup create
sudo misbot backup verify
sudo df -h /opt/matrix-stack
```

При локальном MAS ожидаются `consistent_backup` с путём и SHA256, затем две успешные проверки
`temporary_database_restore` с `inventory_compared=true`. Дамп и упаковка ненадолго
останавливают Synapse, MAS, JWT, реферального бота и его controller,
административного бота. Федеративный backend/API не может менять данные
параллельно: все его записи используют ту же operation lock.
Копия сохраняет identity API, bot session/device/crypto store, peers, заявки и
checkpoints; проверка включает восстановление crypto SQLite и integrity_check.
Копия также включает `settings/site.env`, assets главной страницы, Caddyfile и
checkpoints применения сайта. Восстановление возвращает состояние на момент копии;
изменения, сделанные после неё, автоматически не сохраняются.
До окончания операции новые
входы и сообщения могут быть недоступны. После неё запускаются только ранее
работавшие службы. Время зависит от объёма данных, скорости диска и сети;
прогресс выводится строками JSON. Не запускайте одновременно обновление,
перенос, смену пароля или хранилища.

`restore-check` восстанавливает дампы во временные базы и удаляет их, не заменяя
рабочие. Это проверка дампов, а не полноценная проверка новой машины. Не удаляйте
предыдущую проверенную копию до проверки новой. При ошибке диска освободите место
вне рабочих данных и повторите `backup`, затем `restore-check`.

Для S3 обычный `backup` включает только файлы, уже находящиеся локально. Если
локальные оригиналы исчезли, используйте `backup-external`: эта операция также
сверяет все объекты live-prefix и скачивает отсутствующие оригиналы.

### Одноразовые ключи после восстановления

дамп Synapse сохраняет схему `e2e_one_time_keys_json`, исключая
данные этой таблицы. При восстановлении старого архива установщик очищает
только эту таблицу целевой базы до запуска Synapse. `restore-check` проверяет
такую очистку во временной базе; перед первой `restore-activate` выполняется
Повторная проверка для старых staged-копий. Работающий источник не очищается.

В выводе ожидается `restored_one_time_keys`, `passed=true`, `remaining=0`.
Это предотвращает повторную выдачу уже использованных одноразовых ключей;
клиенты загружают свежие. Постоянные ключи сервера и устройств, cross-signing,
резервные копии ключей комнат и история сохраняются. Серверная копия сама
по себе не заменяет клиентские ключи для расшифровки истории.
Основание: [инструкция Synapse](https://element-hq.github.io/synapse/latest/usage/administration/backups.html).

Если PostgreSQL недоступна или таблица заблокирована, target остаётся staged;
исправьте доступность/блокировку и повторите исходную `restore`/`restore-local`,
`database-recover` либо `restore-activate`, указанную сообщением. Не запускайте
Synapse вручную. Уже активированная установка отвергает повторную активацию
без очистки новых ключей. Физическая копия внешней PostgreSQL может содержать
OTK: при восстановлении пользуйтесь проверенным логическим архивом и указанными
операциями, не запускайте Synapse поверх старой физической копии самостоятельно.
Проверяйте восстановление и отправку зашифрованных сообщений отдельно от проверки дампов.

## Копии при внешнем MAS

При `MAS_MODE=external` Misbot копирует только базу Synapse, локальные настройки,
историю, медиа и ключи устройств ботов. База, пользователи, пароли, OAuth-сессии
и ключи самого внешнего MAS **в архив не входят**. Misbot не останавливает и не
копирует внешний MAS. Согласованность относится к локальному Synapse; отдельную
копию внешнего MAS создаёт его владелец.

В архиве используется формат 3 с явным признаком `external_mas.snapshot=not-included`.
`backup verify` проверяет один дамп Synapse. Форматы 1 и 2 с локальным MAS
по-прежнему проверяют и восстанавливают две базы. Ненужный дамп MAS для внешнего
варианта не создаётся.

`backup restore` восстанавливает Synapse в новую локальную PostgreSQL и оставляет
чат выключенным. Для источника с внешней PostgreSQL используйте `backup restore-local`.
Адрес и общий ключ внешнего MAS сохраняются. Перед активацией сохраните или
восстановите его соответствующее состояние отдельно, включая прежние аккаунты,
устройства и сессии; затем остановите источник и переключите DNS Matrix:

```bash
sudo misbot backup activate --confirm source-stopped --external-mas-confirm preserved-state
```

`preserved-state` — ваше явное подтверждение сохранения внешнего MAS. Misbot
проверяет HTTPS и права управляющего приложения, прежние идентификаторы
администратора и ботов, а также сохранённые сессии устройств. После старта
Synapse проверяется приём прежних токенов ботов. Эти проверки не доказывают,
что отдельная копия внешнего MAS полная или соответствует нужному моменту.
При несовпадении аккаунта, устройства или сессии запуск прекращается;
заменяющие аккаунты и ключи автоматически не создаются.

Удаление установки очищает выбранные данные Synapse и локальные настройки;
сам внешний MAS, его аккаунты, базы и ключи сохраняются.

## Полная зашифрованная копия в независимом S3

Для S3 используются HTTPS,
Signature V4 и приватный bucket. Копии требуют отдельного bucket либо prefix,
не пересекающегося с live-prefix медиа. Другой prefix того же bucket не защищает
от удаления bucket или компрометации общего аккаунта; для независимой копии
используйте отдельное хранилище и учётную запись.

Пакет `cryptography` используется только для шифрования и расшифрования;
команды внешних копий устанавливают `python3-cryptography` при необходимости.
Локальные копии, просмотр и отключение расписания, а также удаление установки
могут работать без него. При отсутствии пакета шифрованный архив не создаётся
и не заменяется незашифрованным.

Создайте закрытый файл на VPS:

```bash
sudo touch /root/matrix-backup-s3.env
sudo chmod 600 /root/matrix-backup-s3.env
sudo nano /root/matrix-backup-s3.env
```

Заполните шаблон реальными значениями. `region` используется при подписи запросов;
укажите регион из документации провайдера, даже если он присутствует в endpoint.

```dotenv
S3_BUCKET=example-private-backups
S3_REGION=ru1
S3_ENDPOINT_URL=https://s3.example.invalid
S3_ACCESS_KEY_ID=EXAMPLE_ACCESS_KEY
S3_SECRET_ACCESS_KEY=EXAMPLE_SECRET_KEY
S3_PREFIX=matrix-backups/example.org/
```

Создайте ключ один раз, вне каталога установки:

```bash
sudo misbot backup key create --key /root/matrix-backup.key
sudo misbot backup external create --config /root/matrix-backup-s3.env --key /root/matrix-backup.key
```

Ожидается `backup_recovery_key` с `created=true`, затем
`encrypted_external_backup` с `passed=true`, object key, двумя SHA256 и путём
к приватному `catalog.json`. Повторное создание ключа в существующем файле
отклоняется без замены. Ключ содержит 32 случайных байта: не вводите пароль
вместо него. Сохраните ключ и catalog по защищённому каналу на другой машине,
отдельно от зашифрованных копий, с доступом только владельцу. Потеря ключа
делает все соответствующие копии невосстановимыми. Не выводите ключ командой
`cat`, не включайте его в архив сервера и не передавайте аргументом команды.

Пока службы записи остановлены, команда сверяет S3-медиа с локальными файлами,
восстанавливает отсутствующие оригиналы и создаёт согласованный архив. Конфликт
содержимого останавливает операцию без перезаписи локального файла. Требуется
место для оригиналов, архива, зашифрованной и скачанной проверочной копий.
Затем службы запускаются, архив шифруется блоками AES-GCM с отдельным ключом
архива, отправляется, проверяется отсутствие анонимного доступа, скачивается и
проверяется после расшифрования. Эта последняя проверка ещё не запускает БД.

При ошибке подключения проверьте env приватно и повторите ту же команду.
Проверка анонимного доступа повторяет временный HTTPS/DNS/timeout
или HTTP502/503/504 отказ до трёх раз, с паузой2s; до подтверждённого403/404
архив не объявляется проверенным. HTTP200 означает публичный объект и немедленный
отказ. Ошибка проверки сертификата требует исправления endpoint/CA; TLS не
отключается. `backup_privacy_retry` сообщает этап и следующую попытку без URL,
signed requests и секретов. При исчерпании попыток сохраните local snapshot/key,
исправьте ресурс и повторите исходную backup-external команду.
Исходные данные, ключ и локальная копия сохраняются. При обрыве связи сначала
проверьте, завершилась ли команда на VPS: просмотрите приватный catalog и
`sudo misbot status`. SIGINT/SIGTERM во время создания
архива возвращают ранее работавшие службы. После аварийного выключения или
SIGKILL сохраняется private `backup-writers.json`: обычный повтор backup,
up или update откажется менять установку до восстановления. Выполните:

```bash
sudo misbot status
sudo misbot backup recover
sudo misbot check
```

Успех — `backup_recovery pending=false`: возвращены только службы, работавшие до
снимка. Повтор recovery ничего не меняет. Пока исходный процесс существует,
recovery откажется; дождитесь его завершения. При сбое запуска журнал сохраняется:
исправьте причину по приватным журналам и повторите backup-recover.
Для замороженного источника или staged restore recovery оставляет запись
остановленной (`kept_stopped=true`); вместо check следуйте инструкции переноса.
Не удаляйте журнал и не запускайте замороженный источник до решения о возврате.
При обновлении используйте новый доверенный комплект.
Повтор создаёт новый объект. После неудачной загрузки установщик запрашивает
удаление только уникального объекта этой попытки. Отказ удаления не
скрывает первоначальную ошибку: `external_backup_cleanup` сообщает
`delete_requested=false` и путь приватного catalog. Local snapshot/key и
прежние проверенные копии сохраняются. Непроверенная копия не пригодна для
восстановления. Для повторной очистки выполните по SSH на исходной установке:

```bash
sudo misbot backup external cleanup --config /root/matrix-backup-s3.env --catalog '/opt/matrix-stack/stages/external-backups/ИМЯ_ПОПЫТКИ/catalog.json'
```

Замените полный путь catalog на `private_catalog` из сообщения; не вводите
пароли, ключи или токены в команду. Используйте тот же private S3 env, что при
создании копии. Команда не останавливает службы, не удаляет локальный архив и
не требует recovery key. Она проверяет Root/ownership/lock, private file,
bucket/prefix/region/endpoint, unique имя и `upload_verified=false` до запроса.
Успех — `delete_requested=true`, `catalog_updated=true`; повтор с сохранённой
отметкой сообщает `already_requested=true` и не запрашивает удаление снова.
Запрос удаления не доказывает освобождение места: versioning/retention
провайдера могут сохранять старую версию. `unverified_object_may_remain=true`
сознательно не обещает физического удаления. Проверенные, чужие и legacy
catalog до эта операция отвергает до S3 мутации.

При `delete_requested=false` исправьте DeleteObject permission/сеть и повторите
ту же команду. При `catalog_updated=false` сохраните сообщение и проверьте
свободное место/права: отметка могла не сохраниться, повтор может отправить
новый delete request только тому же unique object. Не удаляйте prefix целиком.
Legacy unverified объект проверяет администратор через консоль провайдера по
его приватному catalog; автоматическое подтверждение storage identity для
такого catalog отсутствует. После очистки повторите исходную `backup-external`
и дождитесь полного verified download; cleanup не заменяет эту проверку.
Автоматический timer описан ниже. Удаление старых копий пока выполняет
администратор после проверки новой независимой копии; retention не автоматизирован.

## Регулярные копии через systemd

Установка расписания сначала создаёт реальную копию и проверяет её дампы
во временных БД: Synapse и MAS при локальном MAS, только Synapse при внешнем.
Внешний MAS сохраняют отдельно по [условиям выше](#копии-при-внешнем-mas).
Timer включается лишь после успешной проверки.
Команды выполняют по SSH на активном initialized сервере; они могут ненадолго
остановить запись. После настройки проверьте реальный запуск таймера и восстановление копии.

Для local media без S3 можно использовать локальную копию ежедневно в 03:00 UTC:

```bash
sudo misbot backup schedule local --calendar '*-*-* 03:00:00 UTC'
```

Локальный архив не защищает от потери VPS. Для полной зашифрованной внешней копии,
в том числе при media S3, сначала подготовьте независимый backup env/recovery key
по предыдущему разделу, затем:

```bash
sudo misbot backup schedule external --config /root/matrix-backup-s3.env --key /root/matrix-backup.key --calendar '*-*-* 03:00:00 UTC'
sudo misbot backup schedule status
```

Выражение календаря берут в кавычки. Оно проверяется `systemd-analyze calendar`;
при неверном вводе timer не изменяется. Успех — `backup_schedule enabled=true`
с именем unit. Status показывает `NextElapseUSecRealtime`, `LastTriggerUSec`,
`Result` и `ExecMainStatus`; после успешного запуска service имеет Result=success,
ExecMainStatus=0. Systemd может сбросить эти значения после выгрузки неактивной
службы, например при отключении timer. status отдельно показывает
`last_verified` с UTC-временем, сохранённым после успешной проверки копии.
При внешнем MAS эта запись не подтверждает копию или восстановление внешней
службы авторизации. `execution_metadata_available=false` означает, что
показанные systemd Result/Status не подтверждают последний запуск. Отсутствие
last_verified у прежней версии означает отсутствие записи, а не потерю архива.
Last_verified — последняя успешная копия, не результат всех последующих попыток;
ошибки смотрите в service и приватном журнале. После переноса на иной ROOT старая
запись не подтверждает проверку на новой машине. В `stages/backup-scheduled.log` ожидается
`scheduled_backup_verified passed=true`: проверены все включённые дампы,
для внешней копии также download/manifest. Просматривайте файл только приватно,
он содержит сведения о вашей копии.

Timer Persistent догоняет пропущенный запуск после включения машины;
активная oneshot-служба не стартует второй раз. Общая installer lock также
исключает одновременный backup/update/rotation. Повтор configure проверяет
новую копию, затем заменяет своё расписание. При отказе назначения прежний timer
сохраняется; чужой unit по тому же имени не заменяется. После сбоя установки
unit проверьте status и повторите configure; рабочие данные не удаляются.
после успешного rollback units сообщение прямо подтверждает возврат
прежних units/configuration и сохранность admission-копии, даёт точную команду
`backup-schedule-status` для этого ROOT. Затем исправьте systemd ошибку и повторите
исходную команду настройки. Это подтверждение появляется после завершения rollback;
ошибка самого rollback остаётся ошибкой и не объявляется восстановлением.
Описание timer: [официальный systemd v255](https://github.com/systemd/systemd/blob/v255/man/systemd.timer.xml).

При отказе S3, недостатке места, исчезнувшем ключе или неверных credentials
service сообщает failure; следующая попытка не удаляет предыдущие проверенные
копии. Исправьте причину, сохраните исходный recovery key и повторите configure
либо запустите указанную status службу через `sudo systemctl start ИМЯ.service`.
После SIGKILL сначала выполните backup-recover по предыдущему разделу.
Timer не освобождает место автоматически: контролируйте `df -h` и рост архивов.

```bash
sudo misbot backup schedule disable
sudo misbot backup schedule status
```

Disable останавливает будущие срабатывания; уже работающий backup продолжает
проверку и cleanup. Если backup ещё держит installer lock, команда disable
сообщит busy: дождитесь завершения и повторите её. Для немедленного отключения
будущих срабатываний используйте `sudo systemctl disable --now ИМЯ.timer`,
а после завершения backup повторите installer disable для сохранения record.
Если нужно прервать сам backup, используйте
`sudo systemctl stop ИМЯ.service` и затем status/backup-recover. Не удаляйте установку до завершения
службы. Перед переносом отключите timer на источнике; frozen/staged сервер
откажется выполнять scheduled backup. На новой машине передайте private env/key,
проверьте status и настройте timer заново после активации. Архив не включает
unit в /etc/systemd/system и внешний recovery key. При ином пути установки
перенесённый record сообщает needs_reconfigure и не управляет timer источника.

## Скачивание и восстановление на другой машине

Передайте приватные S3 env и ключ по SSH, ограничьте права `chmod 600` и владельца
`root`. Возьмите object key и SHA256 шифрованного файла из сохранённого catalog.
Из распакованного доверенного комплекта:

```bash
sudo python3 misbot.py backup fetch --config /root/matrix-backup-s3.env --key /root/matrix-backup.key --object OBJECT_KEY --sha256 CIPHERTEXT_SHA256 --output /root/matrix-restored.tar.gz
sudo python3 misbot.py backup restore --archive /root/matrix-restored.tar.gz --sha256 ARCHIVE_SHA256 --public-ip 203.0.113.20 --directory /opt/matrix-stack
```

До успешной активации на чистой машине системная команда `misbot` ещё
не зарегистрирована. Для всех последующих staged-проверок, отключения Vault
и активации используйте тот же проверенный комплект: заменяйте `sudo misbot`
на `sudo python3 misbot.py` и добавляйте `--directory /opt/matrix-stack`.
Активация копии актуального комплекта регистрирует системную команду.
Если старый архив её ещё не содержит, продолжайте из проверенного совместимого
комплекта с `--directory` до обновления runtime по [руководству CLI](cli.md).

Замените заглавные заполнители и IPv4 значениями своей копии и новой машины.
`backup-fetch` сообщает `external_backup_download passed=true` и SHA256
расшифрованного архива. Он не заменяет существующий файл. При неверном ключе,
SHA256, усечённом или подменённом файле архив назначения не публикуется.
Повторите с правильными реквизитами и новым путём. Успех fetch означает проверку
шифрования, архивов и исходников; затем необходимы `restore`, сравнение данных,
`restore-check`, запуск и клиентские проверки.

`restore` допускает только пустой каталог либо продолжение той же незавершённой
операции. Ожидается `restore_staged` с `writers_disabled=true`. Перед запуском
остановите источник и выполните маршрут переноса из [README](README.md#8-резервная-копия-и-восстановление).
Не запускайте две независимые установки с одним `server_name`.

`restore-activate` также отвергает target writers в состоянии Docker
`paused`: после `docker unpause` они могли бы продолжить запись. Отказ происходит
до preflight и очистки восстановленных одноразовых ключей; staged данные и журнал
сохраняются. На целевой машине выполните `sudo bash /opt/matrix-stack/install.sh down`,
убедитесь через `status`, что её контейнеры удалены, затем после остановки источника
Повторите `sudo misbot backup activate --confirm source-stopped`.
При старом доверенном архиве используйте текущий совместимый комплект для
`restore`/`restore-local`: он устанавливает обновлённую защиту в staged target.

Если архив содержит подключение Vault, а новая копия будет использовать локальные
секреты или source ещё использует этот Vault path, после `restore_staged` до
активации выполните :

```bash
sudo python3 misbot.py credentials vault disconnect --directory /opt/matrix-stack
```

Ожидается `vault_disconnected`, `local_files_retained=true`,
`remote_versions_retained=true`. PostgreSQL может работать, остальные target
службы должны быть остановлены. Это предотвращает публикацию локальных изменений
в общий Vault path исходника. После активации можно подключить собственный новый
пустой path по [vault.md](vault.md); AppRole-файлы вне server archive доставляются отдельно.

restore сохраняет проверенный исходный архив в приватном
`backups/` назначения и создаёт относительную `latest.tar.gz`. Последующий
`restore-check` использует эту копию; исходный download можно хранить отдельно.
Для копии архива нужно дополнительное свободное место размером с download.
Повтор проверяет существующий архив по SHA256 и не заменяет чужой файл.
После прерывания повторите исходную restore-команду. Не создавайте абсолютные
latest-ссылки вручную: они отвергаются при продолжении восстановления.

## Финальная копия перед переносом

Сначала обновите установленный сервер доверенным комплектом по README.
На источнике выполните:

```bash
sudo misbot backup move export
sudo misbot backup verify
sudo misbot status
```

`move-export` сохраняет migration freeze и останавливает Synapse/MAS/JWT/бота.
Для S3 сообщения `migration_external_media_started` и
`migration_external_media_snapshot` означают проверку всех live-prefix объектов
и докачивание отсутствующих оригиналов. Длительность зависит от объёма медиа,
диска и сети; требуется место для временной сверки даже существующих файлов.
Успех — `migration_source_frozen` с архивом и SHA256, проверки восстановления
всех включённых дампов (Synapse и локального MAS);
writers остаются остановленными. Другой успешный backup не подтверждает этот
финальный снимок.

Архив пока локальный и открытый. До удаления источника создайте независимую
зашифрованную копию через
`sudo misbot backup external create --config PRIVATE_S3_ENV --key KEY_FILE`, затем
`sudo misbot backup verify`, скачайте её и восстановите на другой машине по инструкциям
выше. На frozen source эта операция также сохраняет остановку записи.
Перед переносом внешних PostgreSQL/Vault/OIDC services нужна их собственная
согласованная копия: содержимого Matrix архива для их восстановления недостаточно.

При ошибке credentials/сети/TLS/диска не переносите старый или неполный архив.
Источник остаётся отмечен frozen; проверьте `status`, исправьте причину приватно
и повторите `move-export`. После прерывания дождитесь освобождения общего lock.
Если выбираете отмену, сначала остановите writers назначения и верните DNS
на источник, затем `sudo misbot backup move abort --confirm target-stopped`
и `check`. Подтверждение не проверяет другую машину автоматически. Не запускайте
Обычный `up` и не снимайте freeze вручную. Public DNS/client acceptance/final
provider sync и проверенная внешняя финальная копия остаются обязательными
условиями вывода старой машины; приёмку текущего сценария выполняйте отдельно.

## Состав и границы восстановления

файлы с общим inode записываются в полный архив отдельными regular
payloads. Это сохраняет пригодность копии, если SIGKILL оставил скачанный S3
original и scratch как две жёсткие ссылки. Исходные файлы этим действием не
удаляются. Symlink, FIFO и другие специальные файлы в managed payload
отклоняются до их чтения. Исключение — штатный Unix socket
`data/referral-control/bot-run/control.sock`: он не содержит сохраняемых данных,
не копируется и создаётся управляющей службой при запуске. Неизвестные socket
отклоняются. Сохраните установку и существующие копии, выясните
происхождение такого файла и повторите исходную backup/move-export команду.
Не удаляйте неизвестные `.matrix-s3-*` по маске: после аварии сначала проверьте
`status`, freeze и доступность ресурса. Обычный `check` требует работающих
служб и при frozen source ожидаемо сообщает об остановленных writers.

Полный архив включает логический дамп Synapse и, при локальном MAS, дамп MAS,
роли локальной БД,
проверочные количества записей, `server_name`, настройки OAuth и S3,
внутренние credentials, signing key Synapse, ключи локального MAS, конфигурации, доверенный
комплект исходников, сертификаты Caddy, медиа, сессию и криптобазу referral-бота,
cross-signing keys бота, его диалоги и базу владения приглашениями.
`backup-external` добавляет все объекты live S3-prefix и их SHA256 inventory.
Журналы этапов, старые резервные копии и внешний ключ расшифрования не включаются.
Внешний Vault, Dex и произвольные другие приложения требуют своих резервных
копий; архив стека не является копией их хранилищ. Восстановление режима внешней
PostgreSQL в локальную реализовано отдельной командой ниже; серверная проверка
отмечается отдельно. Восстановление в другой внешний кластер пока не реализовано:
не объявляйте проверку её дампов проверкой переезда.

Архив сервера сохраняет зашифрованные события и вложения, но не все ключи устройств
пользователей. Для чтения истории нужны сохранённое устройство либо настроенная
клиентская резервная копия ключей и её recovery key/пароль. Вход Google/Telegram
восстанавливает авторизацию, а не расшифровывает историю. Пароли пользователей
в MAS хранятся как хеши; при отсутствии SMTP восстановление по email недоступно.

Перед удалением старой машины восстановите именно внешнюю копию на другой
машине, сравните базы, ключи, media inventory и состояние бота, проверьте вход,
сообщения и вложения. Сохраните финальный archive SHA256 и свидетельство проверок.

## Внешняя PostgreSQL: восстановление в локальную

`restore-local` принимает полный архив локальной или внешней PostgreSQL 18
и импортирует включённые БД в отдельную локальную PostgreSQL 18:
Synapse и MAS при локальном MAS, только Synapse при внешнем.
Внешний MAS сохраняется отдельно по [условиям выше](#копии-при-внешнем-mas).
Это явная смена
размещения при восстановлении снимка. Команда `restore` по-прежнему отвергает
external архив с сообщением о доступном маршруте. Реализация и изолированные
проверки не заменяют полный серверный проход. Проверяйте публичный DNS, реальные клиенты и внешний Vault отдельно. Перенос в другой внешний кластер не поддерживается.

На новой машине, из нового распакованного совместимого комплекта:

```bash
sudo python3 misbot.py backup restore-local --archive /root/matrix-restored.tar.gz --sha256 ARCHIVE_SHA256 --public-ip 203.0.113.20 --directory /opt/matrix-stack
sudo python3 misbot.py backup verify --directory /opt/matrix-stack
```

Замените пути, checksum и IPv4. Каталог должен быть пустым; `init` не нужен.
Ожидаются `restored_database` для каждой включённой БД, сравнение row inventory и `restore_staged`
с database_mode=local/source_database_mode=external/writers_disabled=true.
Запущена только новая PostgreSQL. Исходный внешний кластер не используется:
сетевой доступ и его административный пароль для этого импорта не нужны.
Сохранённые внутренние пароли Synapse/MAS используются для новых локальных ролей;
server_name, ключи, авторизация, медиа и bot state восстанавливаются из архива.
Неиспользуемые external PG settings/connector files удаляются только в назначении;
оригинальный приватный архив сохраняется для восстановления исходного размещения.

Нужно место для распаковки, новых баз и сохранённой копии архива. При ошибке SHA,
непустом чужом каталоге или несовместимых образах импорт не продолжается. При
частичном импорте устраните причину и повторите ту же `restore-local` команду.
Журнал привязан к SHA/IP и явной database policy: переключение на `restore`
посреди операции отклоняется. При занятом lock дождитесь завершения дочернего
процесса; не удаляйте guard/journal и не запускайте writers вручную.

Повтор из нового совместимого распакованного комплекта обновляет
исходники самого установщика в незавершённом target перед генерацией конфигурации.
Данные и секреты из target этим обновлением не заменяются. Генератор допускается
только как дочерний процесс текущего восстановления с тем же SHA и унаследованной
блокировкой; остальные операции остаются закрыты до `restore_staged`.
Если восстановление остановилось на генерации в стадии `files_ready`,
сохраните каталог и архив и повторите исходную команду из совместимого комплекта
с теми же путями, SHA, IP и выбором `restore`/`restore-local`.

S3 сохраняет прежний bucket/prefix: для полного восстановления без исходных
локальных файлов нужна полная `backup-external` копия медиа. Vault snapshot
после изменения settings становится dirty; старый external snapshot не следует
использовать для возврата конфигурации назначения. Сохраните private cache и
после принятого переключения выполните `vault-sync` по [vault.md](vault.md).
Внешний Vault имеет отдельную копию и условия доступа.

Серверная копия сохраняет ciphertext и состояние серверного бота, но не room
keys произвольного клиентского устройства. Для своей истории
пользователь восстанавливает ключи через доверенное устройство/secure backup
и собственный recovery key. Храните эту возможность восстановления отдельно
от VPS; password reset и полный серверный архив её не создают.

Для финального переезда остановите источник, восстановите окончательный снимок,
проверьте включённые БД и вложения, смените DNS и выполните
`sudo python3 misbot.py backup activate --directory /opt/matrix-stack --confirm source-stopped`
по README. Смена режима через снимок требует перерыва записи; это не zero downtime
или online replication. Возврат после новых writes на назначении требует новой
согласованной копии этих writes, а не запуска устаревшей source БД.
