# Миграции данных при обновлении Misbot

Версия продукта и версия схемы данных независимы. Релиз 1.1.0 объявляет
`data_schema_version: 1` в `release.json`; `data_migrations.py` содержит
последовательную историю миграций. Пропуск промежуточных релизов выполняет все
недостающие шаги по порядку. Опубликованные ID и SQL менять нельзя.

`misbot update apply` и `misbot update latest`, включая запуск из панели:

1. Проверяют manifest, версию, допустимый переход компонентов и текущую схему
   данных. Неизвестная схема или изменённая история миграций останавливает
   обновление до копии и замены исходников.
2. Проверяют свободное место, создают согласованную полную копию и проверяют
   восстановление PostgreSQL. Затем сохраняют checkpoint и update journal.
   Для существующей базы панели дополнительно создаётся согласованный SQLite
   checkpoint через online backup API в `stages/updates/…/data-migrations/`;
   он сохраняет целостность даже при работающем host-контроллере. В
   existing-compose этот checkpoint находится в `.misbot/source-updates/…/`.
3. Применяют миграции данных до копирования исходников и запуска нового runtime.
   DDL, запись истории и `PRAGMA user_version` выполняются в одной SQLite
   транзакции `BEGIN IMMEDIATE`, без промежуточного commit. SQLite сериализует
   запись с действующей службой. При сбое транзакция откатывается; после
   прерывания повторный запуск выполняет только недостающие шаги.
   Незавершённый SQLite journal после аварийного завершения восстанавливает
   сама SQLite перед проверкой схемы; удалять journal вручную не нужно.
4. Проверяют запуск, версию и revision. При ошибке проверяют совместимость
   данных со старым runtime и восстанавливают предыдущие исходники.

Схема 1 управляет только `data/admin-panel/panel.sqlite`: настройки, пользователи
и очередь доставки. Прежняя неверсионированная схема считается схемой 0.
Миграция сохраняет её строки, регистр текстов, уведомления о версиях и ID
доставки. Defaults добавляются только при отсутствии значения. При первом
старте пустая панель проходит тот же путь автоматически.

В той же транзакции обновляется совместимое значение `settings.welcome`, если
оно точно совпадает с прежним штатным приветствием, включая варианты без точки
после адреса реферального бота. Новый текст содержит название сервера и полные
ссылки на бота и администратора из настроек установки. Подстановки раскрываются
до записи, чтобы и прежний работающий контроллер existing-compose мог отправлять
готовое приветствие сразу после обновления исходников. Пользовательские тексты,
прочие настройки, пользователи и очередь доставки сохраняются. Повторный запуск
не записывает приветствие заново и не создаёт сообщений. SQLite checkpoint
содержит текст до замены; прерывание до commit откатывает замену вместе с остальной
транзакцией. Схема 1 и опубликованные ID/SQL миграций остаются прежними.

Допущенные миграции остаются совместимыми с читателями схемы 0. Поэтому откат
к прежним исходникам **сохраняет актуальные данные**, не восстанавливает старую
очередь и не повторяет уже отправленные сообщения. При неизвестной/повреждённой
схеме прежний runtime не запускается; journal и данные сохраняются для
`misbot update recover` из доверенного комплекта. Одного изменения номера
схемы для несовместимой миграции недостаточно: нужен отдельный реализованный
план остановки writers, проверенного восстановления и ограничения downgrade.

Подключённый existing-compose проверяет и применяет ту же миграцию данных
панели перед обновлением публичных исходников; его Synapse/MAS не перезапускаются
и не мигрируются этим кодом. Его собственная проверенная копия используется
перед применением.

Схемы Synapse/MAS обновляются штатными механизмами компонентов только для
явно допущенных переходов. Произвольные component upgrades и major PostgreSQL
не поддерживаются. Этот механизм не меняет `server_name`, OAuth issuer,
Matrix devices/crypto stores, ключи, расположение медиа/S3 или формат настроек.
`config migrate` остаётся явной отдельной операцией. Для каждого нового релиза
проверяется совместимость всех этих данных с поддерживаемыми предыдущими
версиями, включая пропуск релизов, повторный запуск и восстановление после сбоя.
