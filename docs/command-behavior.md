# Поведение команд и проверка сценариев

Руководство для разработчика и рецензента изменений команд: найти ожидаемый результат, увидеть
пробелы проверки и запустить только связанный сценарий. Для управления сервером используйте
[справочник CLI](../installer/cli.md), а этот каталог читайте при изменении или проверке поведения
продукта.

`ci/command_behavior.json` связывает публичные команды с ожидаемым поведением и
точными тестами. Реестр маршрутов остаётся в `installer/cli_commands.py`; каталог
не добавляет команды и не определяет права выполнения. Это контракт проверки
продукта, не список выполненных серверных операций. В установочный архив файлы
`ci/` не входят.

## Найти команду или сценарий

Из корня репозитория, с доступным Python 3:

```bash
python3 ci/command_behavior.py
python3 ci/command_behavior.py --command 'backup create'
python3 ci/command_behavior.py --scenario update.exit
python3 ci/command_behavior.py --gaps
python3 ci/command_behavior.py --command 'backup create' --json
```

Обычная команда только читает исходники и каталог. Она показывает ошибки
согласования, число пробелов и группы риска. `--command` раскрывает роли, условия,
инварианты, интерфейсы, сценарии и пробелы одной команды. `--gaps` перечисляет
пробелы по командам; `--strict-gaps` возвращает ненулевой код при наличии пробелов
в выбранной области. Без него неполное тестовое покрытие видно, но не блокирует
проверку согласованности каталога.

Успешная проверка сообщает `Catalog valid` и `Tests not run`: команды, сценарии и ссылки
согласованы, но тесты ещё не запускались. При ошибке согласования сначала исправьте указанный путь,
ссылку на тест или карту маршрутов, затем повторите обычную команду. Не убирайте `gap` ради
успешного результата.

| Режим | Успешный результат | Ненулевой код |
| --- | --- | --- |
| Обычная проверка / `--command` | Каталог согласован; пробелы остаются видимыми | Ошибка каталога или аргументов |
| `--strict-gaps` | В выбранной области нет объявленных пробелов | Есть пробелы либо ошибка каталога/аргументов |
| `--run ID` | Связанные тесты выполнены и сценарий получил `passed` | Выполнение не подтвердило сценарий либо ввод некорректен |

Новую, удалённую или дважды описанную команду реестра проверка отвергает. Прямые
действия SSH UI сверяются с `ui_actions.MENUS`; встроенные шаги мастера обозначены
отдельно. Для Telegram сверяются литералы slash-команд, callback-семейств и
статических кнопок. Для Matrix admin сверяются сравнения `text === "…"`.
Изменение распознаваемого набора требует обновить сценарии и явную карту.
Это ограниченные проверки исходников: динамически собранные маршруты, регулярные
выражения Matrix, контекстные диалоги и весь роутер referral автоматически
не извлекаются. Они требуют просмотра обработчика и профильных тестов.

## Что означает покрытие

- **Объявлено:** записаны условия, ожидаемый ответ и допустимое состояние после
  операции. Это может быть пока непроверенное требование с явным `gap`.
- **Связано:** существует конкретное объявление теста. Это не означает, что он
  был выполнен, прошёл или проверяет весь сценарий.
- **Проверено этим запуском:** явный `--run` действительно выполнил указанные
  тесты и вывел их результат. Пропуск, expected failure, отсутствие теста,
  ненулевой код, ошибка импорта и timeout не считаются успешной проверкой.
- **Проверено на сервере/клиенте:** отдельная приёмка. Изолированный тест с mocks
  не подтверждает реальные DNS, MAS, Matrix E2EE, systemd или доставку сообщений.

Сценарий содержит уровень `routing`, `presentation`, `backend` или `interaction`. Проверка
argv/root/парсера не закрывает пробел поведения операции. Проверка форматирования закрывает только
вывод, а не изменение состояния, повтор или восстановление. Backend-тест не подтверждает видимый
результат UI/бота: для этого нужна ссылка уровня presentation/interaction. Даже связанный тест
закрывает только явно перечисленные аспекты конкретного сценария. Явный `gap` другого сценария на
той же оси остаётся видимым, даже когда часть случаев связана с тестами. Процент «команд полностью
проверено» не вычисляется.

Аспекты: `success`, `failure`, `permissions`, `preconditions`, `interruption`,
`retry`, `output`, `state`. Пробел означает отсутствие сопоставленного доказательства,
а не обязательно отсутствие теста в репозитории или дефект продукта. Для редкого
неприменимого случая нужно объяснить причину в `gap`, а не ставить фиктивный pass.
Сценарии и пробелы дополняются по мере исследования конкретной операции.

## Явный запуск сценария

```bash
python3 ci/command_behavior.py --run update.exit
python3 ci/command_behavior.py --run referral.dedupe
```

Запускаются только точно указанные unittest или node:test из репозитория, без shell-строк. Node
получает один файл и точное имя теста в отдельном процессе; `--test-isolation=none` сохраняет
именованные события для проверки фактического pass/skip вместо агрегированного результата файла.
Каталог связывает изолированные тесты; живую приёмку и сборочные тесты, изменяющие manifest, в этот
маршрут добавлять не следует. Обычные полные suites продолжают запускаться существующим `ci/check.py
tests`; его discovery автоматически включает тест проверки каталога.

Результат `--run` содержит UTC-время, статусы тестов и отпечаток исходников: указанные tests,
каталог/проверяющий скрипт, верхнеуровневые Python/shell-файлы installer и Python/JS-файлы трёх
ботов. Это ограниченная область отпечатка, не аттестация всего окружения, зависимостей или полного
дерева. Если эти исходники изменились во время запуска, результат не считается актуальным pass.
Сырые ошибки tests не включаются в итог: указаны безопасные классы отказа. Для подробного
расследования тест запускается обычным unittest/node runner в подходящем окружении. Отчёт можно
сохранить из stdout отдельно от исходников; сохранённый прошлый результат не подменяет новый запуск
после изменения кода.

При отсутствии зависимости или ошибке импорта подготовьте среду нужного набора тестов и повторите
тот же `--run ID`. При timeout или прерывании считайте результат неподтверждённым; сначала
проверьте, завершился ли дочерний тестовый процесс. Для разбора запускайте конкретный тест штатным
unittest или Node runner. Не добавляйте в каталог тесты, которые требуют действующего сервера,
секретов или меняют установленный стек: этот маршрут предназначен для изолированных проверок.

## Обновление контракта

При добавлении или изменении команды:

1. Добавьте точный путь в одну группу; общие условия и инварианты группы должны
   действительно подходить операции. Уточните доступность CLI/UI/ботов.
2. Опишите поведение до запуска, после успеха, при отказе и неизвестном исходе.
   Для записывающего действия отдельно рассмотрите прерывание и повтор.
3. Свяжите сценарий с точным `file` и `Class.test_method` для Python либо
   буквальным именем верхнеуровневого `test("…", …)` для JavaScript. Ссылка
   только на файл не принимается. Сложные динамические JS-объявления данным
   проверяющим не поддерживаются; требуется обычный именованный тест.
4. Тест должен проверять наблюдаемый результат: например, ненулевой exit при
   `success:false`, отсутствие повторной мутации, сохранённый checkpoint или
   необходимые безопасные поля ответа. Не заменяйте это проверкой наличия
   имени команды в коде или снимком всего длинного текста.
5. Для недостающих проверок оставьте конкретный `gap`. Затем проверьте каталог
   и запустите затронутые тесты. При изменении literal inventory сначала
   изучите новые маршруты; механическое обновление списка не добавляет покрытия.

Приглашения участника имеют отдельные `member.*` сценарии: они не эквивалентны
CLI управления первым установочным кодом. Роли root, MAS admin, список доступа
Matrix-панели и владелец приглашения также разделены. Отсутствующий интерфейс
показывается как `not_exposed`, а не как успешно пройденный тест.
